## 背景と課題

エージェントは動くようになったが、自分で仕事を進めるための手段が足りない。現在のツールは `list_dir` / `read_file` / `write_file` / `load_skill` / `run_skill_script` / `delegate` の 6 つで、次の場所で行き止まる。

- **外の情報が一切取れない。** 検索も取得もないため、モデルが学習した時点までの知識しか使えない。調べ物を頼まれても、手元のファイルを読むことしかできない。
- **大きな木をたどれない。** `list_dir` と `read_file` しかないので、目的のファイルを見つけるには 1 階層ずつ舐めることになる。数往復で `max_iterations` に達し、探しているうちにターンが終わる。
- **ファイルを部分的に直せない。** `write_file` は全文置換で、しかも読み取り 200KB・書き込み 1MB の上限がある (`internal/tools/fs.go`)。大きなファイルは、読むことはできても直せない。
- **任意のコマンドを実行できない。** 走らせられるのはスキルに同梱されたスクリプトだけで、`git` も、ビルドも、試験も呼べない。手元の作業を任せる相手にならない。
- **ツールが増えるほど止まる。** 承認は `Tool.NeedsApproval()` が固定で返す値で決まり、利用者が変えられない。ツールを増やすと確認の回数が増え、自律駆動が成り立たなくなる。

v1 (#694381) はこれらを意図的に外していた。土台を作り終えた今、外していた理由 (承認とサンドボックスの設計が必要になる) は「危険性を受け入れる」という判断で解ける。

## ゴール / 非ゴール

### ゴール

- 検索と取得で、外の情報を使って調べ物ができる。
- 任意のコマンドを実行できる。
- 名前と中身の双方でファイルを探せる。
- ファイルを部分的に直せる。動かせる。消せる。
- 作業ディレクトリの境界を外れてよいかを、エージェントごとに決められる。
- どのツールで確認を求めるかを設定で選べる。
- 対話を求めるコマンドと、終わらないコマンドを扱える。
- 決められないことだけを利用者に問い、それ以外は自分で決めて進み続ける。

### 非ゴール

- **ブラウザ操作。** 取得は HTTP とその本文の抽出までとする。JavaScript を動かさないと出ない内容は取れない。
- **サンドボックス。** 危険性を受け入れる前提なので、隔離する仕組みは作らない。境界と承認だけが歯止めになる。
- **差分形式での編集。** 部分編集は文字列の差し替えに留め、patch や diff は受け付けない。
- **検索結果の保存と引用の管理。** 取ってきたものはその場で使うだけで、溜めない。
- **認証を要する API への汎用クライアント。** 検索の取得元だけが鍵を持つ。
- **端末の再現。** 走らせたままのプロセスとやり取りするのは行単位の読み書きに留める。画面を描き換える相手 (vim、top) は扱わない。
- **問いの保存と再開。** 問いは走っているターンの中でだけ生きる。答えないまま閉じたら、そのターンは前提を置いて進むか終わる。

## 設計案

### 採用案

4 つの決定からなる。

**1. ツールは既存の抽象のまま増やす。** `Tool` インターフェースと `Registry` は変えない。エンジン側にも手を入れない。増やすのは登録するツールと、それが受け取る一式だけである。

**2. 境界をエージェントの属性にする。** いま実行の一式が持つのは作業場所ひとつで、全ツールが必ずその中に閉じる。ここに「境界を課すか」を足し、課さないエージェントは絶対パスを扱えるようにする。相対パスの基準は、どちらの場合もその会話の作業場所のままとする。

境界を丸ごと外さずエージェントの属性にするのは、Tier と同じ考え方による。何ができるかは定義を読めば分かる状態を保つ。上位だけが外に出られて下位は会話の中に閉じる、という使い分けもこれで書ける。

**3. 承認を設定で決める。** ツールが持つ既定はそのままにし、設定に「確認しないツールの一覧」を置いて上書きできるようにする。検索と読み取りは自動、削除とコマンドは確認、といった線引きを利用者が引く。

**4. 対話は「走らせたまま」を別のツール群として持つ。** 終わるまで待つ実行と、走らせたまま読み書きする実行を分ける。前者は 1 回の呼び出しで完結し、後者は起動・読み取り・書き込み・停止の 4 つに分かれる。分けるのは、対話が「出力を読んでから次の入力を決める」ことだからである。1 つのツールに畳むと、読む前に答えを決めることになり、対話にならない。

**5. 問いを道具にする。** 利用者へ問うこと自体をツールにし、答えが返るまでそのターンを止める。本文で問いかけても、それはターンの終わりであって誰も答えない。問いを道具にすれば、答えは次のツール結果として同じ思考の続きに載る。

**6. 検索の取得元を差し替えられる形にする。** 提供元 (`provider`) と同じく、取得元をひとつのインターフェースにまとめる。既定は鍵の要らない取得元とし、設定に鍵を入れれば API を使う取得元へ切り替わる。

### 検討した代替案

- **境界を丸ごと外す。** 最も単純で、実装も設定も減る。採らないのは、定義を読んでも何ができるか分からなくなるからである。委譲した先が意図せず別の場所を書き換えたとき、どのエージェントがそれを許されていたのかを後から辿れない。
- **承認をセッション内で記憶する。** 決める手間が要らないが、会話ごとに聞き直されるため、長く使うほど同じ判断を繰り返すことになる。設定に置けば一度で済む。
- **検索を鍵の要る API に限る。** 結果は安定するが、鍵を取るまで検索が一切使えない。最初の一歩が重い道具は使われない。
- **検索を鍵の要らない取得元だけにする。** すぐ使えるが、先方の HTML が変わると壊れ、逃げ道がない。両方を持たせ、既定を鍵なしにすることで、すぐ使えて壊れても直せる状態にする。
- **部分編集を patch 形式で受ける。** 一度に複数箇所を直せるが、ローカルモデルが行番号を正しく数えられず、当たらない patch を繰り返すことになる。文字列の一致で差し替えるほうが、当たったか外れたかがその場で分かる。
- **対話をコマンド実行の引数だけで賄う (標準入力に答えをまとめて渡す)。** 実装は 1 行で済むが、問いを読む前に答えを決めることになる。何を訊かれるか先に分かっている場合しか使えない。両方を持たせ、先に分かるものは引数で、読んでから決めるものは走らせたままの側で扱う。
- **走らせたままのプロセスを 1 つのツールに畳む (action で分ける)。** ツールの数は減るが、どの引数がどの action で要るのかが定義に書けず、モデルは組み合わせを間違える。渡す定義が増えることは受け入れる。
- **問いを承認の仕組みに載せる。** 経路が 1 本で済むが、承認は可否の二択であり、問いの答えは文である。二択に押し込むと答えが返らない。
- **問わずに常に前提を置かせる。** 止まらないという点では最も強いが、決めようのないこと (どちらの形式で出すか) まで勝手に決めるので、やり直しが増える。止まってよい場面を狭く定義したうえで、その手段を与えるほうが速い。
- **コマンド実行を許可リストで縛る (git と npm だけ、など)。** 事故は減るが、必要なコマンドを足すたびに設定を開くことになり、自律駆動という目的から遠のく。境界と承認で歯止めをかけ、コマンド自体は縛らない。

## 詳細設計

### データモデル

設定に加える項目。

- **検索の取得元** — 名前ひとつ。鍵の要らないものを既定とする。
- **検索の鍵** — 空なら鍵の要らない取得元を使う。入っていれば、それを使う取得元へ切り替わる。
- **確認しないツールの一覧** — ここに載せたツール名は、既定で確認を求めるものであっても確認せずに実行する。`*` ですべて。空なら各ツールの既定に従う。
- **コマンドの実行時間の上限** — 秒。スキル同梱スクリプトの上限とは別に持つ。用途が違い、妥当な長さも違う。

1 ターンのツール呼び出しの上限は、自分で進める前提に合わせて引き上げる。ツールが 6 個だった頃の値のままでは、調べて直して試すという最短の流れですら途中で打ち切られる。上限そのものは残す。ローカルモデルは同じツールを呼び続けることがあり、それを止める手立てが無くなる。

走らせたままのプロセスは会話ごとに束ねる。名前で引き、同じ名前は同じプロセスを指し続ける。会話をまたいで共有しないのは、名前が衝突するからだけではない。ある会話が起動したものを別の会話から止められると、何が動いているかを誰も把握できなくなる。会話を消したとき、Ivis を終えるときには、束ねたものをすべて止める。会話を消したのにその会話の子だけが残る状態を作らない。

同時に走らせておける数と、読まれないまま溜める出力の量には上限を置く。放置されたものが積み上がると機械の資源を静かに食い潰し、伸び続ける出力は起動しっぱなしのサーバー 1 つで記憶を使い切る。溢れた出力は古い側から捨て、捨てたことを読み取り時に示す。

エージェント定義に加える項目。

- **境界を課さないか** — 真のとき、そのエージェントのファイル操作とコマンド実行は会話の作業場所の外へ出られる。省略時は課す (現在の挙動)。

委譲したとき、この設定は継承しない。呼ばれた側の定義がそのまま効く。継承させると、定義を読んだだけではそのエージェントが何をできるか決まらなくなる。

### インターフェース

追加するツールは 13 個。

- **web_search** — 語句と件数を受け取り、見出し・URL・要約の並びを返す。取得元に届かない、鍵が要る、制限された、といった失敗は種類を分けて返す。まとめて「検索できません」にすると、モデルは待てばよいのか諦めるべきか判断できない。
- **fetch_url** — URL を受け取り、本文をテキストにして返す。HTML は本文だけを抜き、飾りは落とす。大きさの上限を超えたら切り、切ったことを結果に示す。切ったと分からないと、モデルは途中で終わる文書を完全なものとして扱う。
- **run_command** — コマンドと、省略できる作業場所と標準入力を受け取る。標準出力・標準エラー・終了コードを返す。時間の上限で打ち切り、その旨を返す。出力は上限で切る。失敗しても実行そのものは成功として扱い、終了コードで示す。コマンドが失敗することは異常ではなく、モデルが読むべき結果である。標準入力は常に与える。何も繋がないと、入力を求めるものは読めるものを持たないまま失敗する。
- **start_process** — コマンドと名前を受け取り、走らせたまま残す。起動直後の出力を待って返す。名前が既に使われていれば断る。
- **read_process** — 名前を受け取り、前回の読み取りより後に出た分を返す。走っているかどうかも添える。次に入力を送るのか待つのかは、それが分からないと決まらない。
- **write_process** — 名前と 1 行を受け取り、標準入力へ送って、それに対する出力を返す。送る前に溜まっている分は流す。前の問いへの答えと、いま送ったものへの応答が混ざると、どちらに対する出力か分からなくなる。
- **stop_process** — 名前を受け取り、止めて片付ける。残っていた出力も返す。
- **ask_user** — 問いと、省略できる候補を受け取り、答えが返るまで待つ。答えをそのまま返す。答えが返らない場面 (問える相手が居ない、空のまま返された) では、自分で前提を置いて進むよう促す文を返す。失敗にはしない。ここで失敗にすると、問いに当たるたびにターンが丸ごと落ちる。
- **find_files** — 名前の形で探す。件数の上限を持ち、超えたら切って総数を示す。
- **search_text** — 中身を探す。ファイル・行番号・その行を返す。件数の上限は同じ扱い。
- **edit_file** — ファイルの中の文字列を差し替える。一致が 0 件のときと 2 件以上のときは断る。どこを直したのか決まらないまま書き換えると、モデルは直したつもりで別の場所を壊す。断るときは一致した件数を返し、モデルが指定をやり直せるようにする。
- **move_file** — 動かす。行き先が既にあれば断る。
- **delete_file** — 消す。ディレクトリを消すかどうかは引数で受ける。既定は消さない。

既定で確認を求めるのは、書き換えるもの (`write_file` / `edit_file` / `move_file` / `delete_file`)、実行するもの (`run_command` / `run_skill_script` / `start_process` / `write_process`)。読むだけのもの (`list_dir` / `read_file` / `find_files` / `search_text` / `web_search` / `fetch_url` / `load_skill` / `read_process`) と、止めるもの (`stop_process`)、問うもの (`ask_user`) は求めない。設定で上書きできる。

`write_process` で確認を求めるのは、走らせたままのシェルへ書けることが、コマンドを実行できることと変わらないためである。起動だけを確認して以後を素通しにすると、承認の線引きが意味を失う。`stop_process` で求めないのは、止めることが誰にとっても安全だからである。暴走を止める操作に確認を挟むと、止めたいときに止まらない。`ask_user` で求めないのは、問うこと自体が何も変えないからである。ここで確認を挟むと、確認のための確認になる。

検索の取得元は、語句と件数を受け取り結果の並びを返すひとつのインターフェースとする。実装を差し替えられるようにするのは将来のためではなく、鍵の有無で切り替わる 2 つを同じ形で扱い、試験でモックを差し込めるようにするためである。

### 処理フロー

**パスの解決** — 境界を課すエージェントは今までどおり。課さないエージェントは、絶対パスをそのまま受け取り、相対パスはその会話の作業場所を基準に解く。境界の判定 (`internal/tools/path.go`) は残し、課さないときだけ通り抜ける形にする。判定の仕組み自体を消すと、課す側の安全も一緒に消える。

**承認** — ツールの既定を出発点に、設定の一覧が上書きする。判定は実行の直前に 1 か所で行う。ツールごとに散らすと、増やしたツールで上書きを忘れる。

**指示文に載せる時刻** — 生成のたびに現在時刻を指示文へ書く。曜日と時差まで含める。そこまで書いてはじめて「いつか」が一意に決まる。載せておかないと、時間に関わる問いのたびにコマンドを打つことになり、しかもその出力が読める保証もない。道具で解ける問題と、そもそも道具を要さない問題を分ける。

**コマンドの出力の文字** — 出力は UTF-8 とは限らない。Windows のコマンドはその環境のコードページで書き出すため、そのまま文字列にすると読めない列になる。妥当な UTF-8 でないときに限り、OS の変換を借りて読み直す。一律に変換しないのは、UTF-8 で書き出す道具のほうが今は多く、そちらを壊すことになるためである。

**コマンドの実行** — シェル越しに走らせる。Windows では `cmd`、それ以外では `sh` を使う。作業場所の既定はその会話のディレクトリで、境界を課さないエージェントだけが別の場所を指定できる。時間の上限に達したら止め、そこまでの出力を返す。何も返さずに打ち切ると、長く走った末に何も分からない。

**シェルへ渡す 1 行** — 書かれたとおりの形でシェルへ渡す。Windows では、引数ごとに引用符を足して命令行を組み立てる標準の作法に `cmd` が従わないため、素通しにすると引用符を含むコマンドが壊れた記号ごと相手に届く。`git commit -m "..."` のような最もよく書かれる形が、その環境でだけ動かない。命令行を自分で組み立て、外側の 1 組だけを外して残りをそのまま解釈させる。

**対話** — 走らせたままのプロセスは、標準出力と標準エラーを 1 本にまとめて受け、読まれるまで溜める。読み取りを待たずに吸い出すのは、パイプが詰まると相手が書き込みで止まり、こちらが読むまで先へ進まなくなるためである。読み取りは、前回より後に出た分が途切れるまで待つ。出力が出た「あと」の静けさを待つのは、対話するコマンドが問いを書き終えるまでに間があるためで、書き終える前に読むと問いの途中だけを読んで答えることになる。止めるときは、シェルの先で走っているものも一緒に止める。シェルだけを殺すと、実際に仕事をしているものが親を失って残る。

**問い** — 問いはツールの実行として始まり、答えはその結果として返る。待っている間ターンは終わらない。問い直しのために会話を送り直させると、そこまでの経過を組み立て直すことになる。どこで受けるかは、その実行がどこから始まったかで決まる。画面から始まった実行は画面の入力欄で、Discord から始まった実行はそのチャンネルへの次の呼びかけで受ける。画面を開いていない相手に、画面でしか返せない問いを出しても答えは返らない。答えられるのは依頼した本人だけとする。走っている依頼の続きなので、他人の発言を答えとして差し込むと、頼んでいない人が仕事の中身を決めることになる。

**進め方の指示** — 「どこまで自分で決めてよいか」を指示文に書く。書かないとモデルは一手ごとに確かめようとし、確かめる先が居ない場面でも確かめるので、ターンは何も進まないまま終わる。止まってよい場面を挙げ、それ以外は進めと明示する。問う手段を持たないエージェントには、代わりに前提を置いて進むよう書く。持っていない道具を勧めると、モデルは本文で問いかけてしまう。

**取得** — 転送量と時間に上限を置く。本文の抽出は、スクリプトとスタイルと飾りを落としたうえでテキストにする。抽出に失敗したら、生のまま切って返す。取れなかったより、読みにくくても中身があるほうが役に立つ。

### 画面

問いは、それを出したツールの行の直下に入力欄として出す。下の送信欄へ書かせてはならない。そこへ書いたものは新しい依頼として保存され、待っている側には届かない。候補があるときは押しボタンとして添えるが、自由に書ける欄も同時に残す。候補どおりに答えるとは限らない。空のまま返せるようにし、そのとき何が起きるか (エージェントが自分で決めて進む) をその場に書く。

Discord では問いを、その呼びかけへの返信の中に文として出し、次の呼びかけを答えとして受ける。押しボタンにしないのは、答えが自由な文だからである。

エージェント設定に「境界を課さない」を足す。真にしたとき、その意味 (会話の外のファイルも読み書きでき、コマンドもそこで走る) をその場に書く。

設定に、検索の取得元と鍵、確認しないツールの一覧、コマンドの実行時間の上限を足す。確認しないツールは、名前を並べるのではなくツールごとの選択として出す。名前を手で書かせると、綴りを間違えたときに黙って確認され続ける。

## テスト方針

- **パスの解決**を、境界を課す場合と課さない場合の双方で検証する。課す側がこれまでどおり上位参照・絶対指定・リンク経由を断ること、課さない側が絶対指定を受け取れること。ここが壊れると境界そのものが意味を失うので最も厚くする。
- **承認の上書き**が、既定で確認するツールに効くこと、`*` が全体に効くこと、載っていないツールが既定のままであることを検証する。
- **edit_file** が、一致 0 件と 2 件以上を断り、そのとき件数を返すことを検証する。
- **run_command** が、終了コードを返すこと、失敗したコマンドを実行の失敗として扱わないこと、時間の上限で打ち切ってそこまでの出力を返すこと、出力を上限で切ることを検証する。
- **検索**は取得元をモックにして、結果の整形と、失敗の種類が保たれることを検証する。
- **取得**は、HTML から本文を抜けること、上限で切ったことが結果に現れることを検証する。
- **対話**を、1 行読んで言い返すだけの手続きに対して検証する。起動時に問いが読めること、送った答えが届くこと。あわせて、読み取りが前回より後に出た分を待つことを確かめる。以前の出力を根拠に「もう途切れている」と判断すると、これから出る応答を待たずに空で戻る。
- **停止**が、止めた相手を実際に終わらせ、束から取り除くことを検証する。会話を消したときにすべて止まることも同じく。
- **引用符を含むコマンド**が、書いたとおりに届くことを検証する。ここが壊れると、最もよく書かれる形が特定の環境でだけ動かない。
- **問い**が、答えをそのまま次の生成へ渡すことを検証する。あわせて、問える相手が居ないときと空の答えが返ったときに、ターンが止まらず前提を置いて進むよう促されることを確かめる。
- **指示文**が、問う手段の有無で書き分けられることを検証する。
- **手動確認** — 実際の検索とページ取得。鍵のある取得元と無い取得元の双方。実際のコマンドを走らせたときの出力の読みやすさ。

## リスクと未決事項

- **鍵の要らない取得元は先方の都合で壊れる。** HTML の形が変われば結果が取れなくなる。壊れたときに鍵のある取得元へ移せることが逃げ道になるが、壊れたこと自体は利用者が気づくまで分からない。
- **打ち切ってもシェルの先は残る。** 上限に達したときに止められるのはシェルだけで、その先で走っているものは出力の口を掴んだまま生き残る。猶予を置いて口を閉じ、そこまでの出力を持って戻る形にしたが、走り続けているもの自体は放置される。
- **コマンドの実行は取り消せない。** 確認を切ったまま走らせると、消えたことを後から知ることになる。既定では確認を求めるが、自律駆動のために切るのは想定された使い方である。
- **出力がコンテキストを食う。** コマンドの出力も取得した本文も、上限を置いても大きい。ローカルモデルの狭いコンテキストでは、1 回の取得で残りを使い切りうる。上限の値は実際に使いながら決める。
- **Windows と POSIX でシェルが違う。** 同じ指示文で書いたコマンドが片方でしか動かない。どちらで動いているかは指示文に載せるが、それでモデルが書き分けられるかは未検証である。
- **走らせたままのものは、こちらの終わり方に付き合わない。** 止める手立ては用意したが、Ivis が落ちた場合には残る。次の起動はそれを知らないので、機械に残ったものを見つけるのは利用者になる。
- **端末を要する相手は扱えない。** 画面を描き換えるもの (vim、top)、パスワードを端末から直接読むものは、行単位の読み書きでは動かない。動かないことはその場では分からず、応答の来ないプロセスとして現れる。
- **問いに答えないまま閉じられる。** 画面を閉じても走っているターンは待ち続け、中断されるまで残る。期限で諦めるのは Discord 側だけである。
- **自分で決めて進むほど、間違った前提のまま遠くまで行く。** 止まらないことと、確かめることは両立しない。置いた前提を答えに書かせることで、後から気づけるようにしているが、書かせられているかはモデル次第である。
- **境界を課さないエージェントの事故を、どこまで見せるか。** 会話の外を書き換えたことは履歴に残るが、一覧からは見えない。目立たせる必要があるかは、実際に使ってから決める。
