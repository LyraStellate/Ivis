## 背景と課題

[全体設計 #258413](2026-09-08-team-session-overview-%23258413.md) の一部。会話は 1 体のエージェントとしか結び付けられず (`store.Session.AgentID`)、複数体が居る会話という入れ物が無い。エージェントの定義も共通の探索パス (`config.AgentPaths`) にあるものだけで、「チームのためだけの担当」を作ると直列の会話の一覧にまで並び続ける。

## ゴール / 非ゴール

### ゴール

- チームセッションを作れる。作業ディレクトリは会話ごとに分かれ、直列の会話と混ざらない。
- チーム専用のエージェントを作成・編集・削除できる。定義は全てのチーム会話で共有され、会話ごとに有効にするかどうかを選ぶ。
- 共通のエージェントも、会話ごとに有効にして使える。ここだけ変えたいときはチームへコピーできる。
- 誰が居るかが右パネルの 1 か所で一覧でき、そこがそのままメンションの宛先の一覧になる。

### 非ゴール

- **メンバーごとの作業ディレクトリ。**
- **チーム構成の雛形化・書き出し・取り込み。**
- **共通エージェントの編集をこの画面から行うこと。** 共通の定義を直すのは設定画面の仕事で、ここでは有効化とコピーだけを扱う。2 か所から同じファイルを書けるようにすると、どちらで直したか分からなくなる。チームエージェントはここが唯一の編集の場所であり、設定画面には出ない。
- **チームセッションから直列への変換、およびその逆。**
- **会話ごとに閉じたエージェント定義。** 一度は採ったが撤回した。理由は「検討した代替案」に残す。

## 設計案

### 採用案

**会話に種類を足す。** セッションは「直列 (series)」か「チーム (team)」のどちらかである。既存の会話は全て直列とする。種類は作成時に決まり、後から変わらない。

出自 (`Source`: web / discord) とは別の軸として持つ。出自は「どこから来た会話か」、種類は「どう進む会話か」であり、混ぜると Discord から来た会話をチームにできるかという問いに答えられなくなる (答えは「できない」で、それは出自の側の制約である)。

**作業ディレクトリは `<作業ディレクトリ>/team/<セッション ID>/`。** #903215 が `series` という段を挟んでおいたのは、まさにこのためである。`config.SessionWorkspace` が種類を見て段を選ぶようにする。メンバーは全員この 1 つを共有する。1 つの仕事を分担しているのだから、成果物の置き場を分ける理由がない。

**定義の置き場は 2 つ、名簿は 1 つ。**

- **共通エージェント** — `config.AgentPaths` にある定義。直列の会話でも使う。
- **チームエージェント** — `<agent_paths[0]>/team/` にある定義。**全てのチーム会話で共有される。**

どちらも「使うには、その会話で有効にする」。有効にしたものの集まりが名簿であり、名簿の中では由来を区別しない。並びは既存の `sortIDs` と同じく Tier 順、同 Tier では ID 順とする。上位から下位へ読める並びは、そのまま指示の流れの向きである。

**チームの定義もファイルに置く。** 形式・検証・読み込みは共通のものと全く同じにする。「エージェント定義はファイルが正」という #528664 の原則をここで折らない。同じ `agent.Agent` として読めるので、指示文の組み立ても、ツールの許可判定も、画面の編集フォームも、共通のものがそのまま使える。

置き場を共通の下の `team/` という段にできるのは、定義の読み込みがディレクトリを掘らないためである。共通の一覧を組む走査は `team/` の中身を見ないので、段を 1 つ作るだけで 2 つの集まりに分かれる。

**集まりは 2 つ別々に持つ。** 1 つの集まりに由来の印を付ける形は採らない。Tier の下限 (共通は 0 を 1 へ引き上げる、チームは 0 を持てる)、委譲先の候補 (直列の会話にチームの担当が並んではならない)、共通の一覧を返す経路、起動時の雛形の書き出し — その全部に「これはどちらか」の分岐が要る。2 つ持てば、振り分けは名簿を組む 1 か所に閉じる。

**ID は共通とチームの全体で一意。** ID はメンションの宛先であり、同時に共有ディレクトリの中のファイル名でもある。同じ会話に同じ名前が 2 つあると `@reviewer` が誰を指すのか決められないし、置き場が 1 つになった以上、別の会話から同じファイル名を作ることもできない。

**チームエージェントは Tier 0 を持てる。** 共通の一覧で Tier 0 を規定エージェントだけに絞っているのは、会話の入口が 2 つある状態を定義の書き換えで作れないようにするためだった ([#528664](2026-09-04-agent-system-%23528664.md))。チームには規定エージェントという入口が無いので、その理由がここには当てはまらない。対等な 2 人組は正当な構成であり、同位どうしは依頼しかできないという規則 ([#640275](2026-09-08-team-session-mentions-%23640275.md)) がそれを支える。

この違いは検証の側と、集まりを読み込むところだけに置く。ファイルに書いた 0 は 0 のまま読み戻せなければならない。読む側で引き上げると、書いた値と読める値が食い違い、どちらが正か決められなくなる。

**規定エージェント (`Fixed`) はチームには居ない。** チームの置き場に規定エージェントと同じ ID の定義を置かれても、規定エージェント扱いにはしない。そうしないと、消せず Tier も変えられないものがチームの中にできる。

**宛先は常に利用者が名指しする。** 会話に「窓口」は無い。誰に頼むかを決めるのは利用者であり、名簿が 2 人以上なら宛先の無い発言は断る。詳しくは [#640275](2026-09-08-team-session-mentions-%23640275.md)。`Session.AgentID` はチームでは「会話を作ったときの記録」に降格し、実行では読まない。

**チームは 1 体から始まる。** 作成時に規定エージェント (`status.default_agent`) を有効にする。空のチームから始めると、最初の発言の行き先が無く、画面は「誰も居ません」としか言えない。ただしその 1 体も外せる — 外して空になった名簿は、送るときに止めて理由を出せばよい。

### 検討した代替案

- **会話ごとに閉じたエージェント定義 (`<data_dir>/sessions/<ID>/agents/`)。** 初版で採り、実際に回してから撤回した。同じ役割の担当を会話のたびに作り直すことになり、指示文を練り込むほど作り直しが重くなる。写しが会話の数だけ増えるので、誤りを直しても既存の会話には伝わらない。共有の置き場へ移し、会話ごとに持つのは「どれを有効にしてあるか」だけにした。既に作られた定義は起動時に 1 度だけ移す。
- **エージェントの定義をデータベースへ持つ。** セッションを消せば外部キーで一緒に消え、後始末が要らない。だが定義を読む経路が 2 つになり、`agent.Set` の読み込み・検証・重複判定を書き写すことになる。ファイルに置けばその全部が既存のまま効く。
- **1 つの集まりに由来の印を付ける。** ディレクトリを分けずに済むが、Tier の下限・委譲先・共通の一覧・雛形の書き出しの全部に分岐が要る。分けるほうが、分岐が 1 か所で済む。
- **共通エージェントはコピーしたものだけが参加できる。** チームが自己完結し、共通の定義を後から直しても過去のチームは変わらない (再現性は高い)。だが同じ定義の写しがセッションの数だけ増え、指示文の誤りを直しても既存のチームには伝わらない。直しが伝わらないことのほうが、日々の使い勝手を損なう。コピーは「ここだけ変えたい」ときの手段として残す。
- **チームのメンバーを共通エージェント全部にする (参加という概念を持たない)。** 名簿を持たずに済むが、宛先の候補が手元の全定義になり、増やすほど選べなくなる。指示文へ載せる名簿も同じだけ太る。チームは「選んで組む」ものである。
- **窓口を 1 体決め、宛先の無い発言をそこへ届ける。** 初版で採り、撤回した。窓口が居ると全部の依頼が窓口を通り、窓口が下へ配り直すだけの手番が毎回 1 つ増える。利用者から見ると、頼んだ相手と動く相手が食い違う。宛先を名指しさせるほうが、手数も理解も少ない。窓口を外せないという制約 (外すと宛先の無い発言の行き先が消える) も一緒に消える。
- **宛先の無い発言を Tier のいちばん上へ届ける。** 決め事が減るが、同位が 2 体居るチームで宛先が決まらない。断って名指しさせるほうが確かである。
- **会話の種類を出自 (`Source`) の値として足す (`team` という出自を作る)。** 列を増やさずに済むが、「Discord から来たチーム」を表せない — 表せないこと自体は今回の非ゴールと一致するものの、将来それを許すときに出自と種類をほどく作業が発生する。最初から別の軸にしておく。

## 詳細設計

### データモデル

**セッション** に 2 つ足す。

- **種類。** 直列かチームか。既存の行は直列として読む。作成時に決まり、更新の対象にしない。
- **有効にしているエージェントの ID の一覧。** 共通とチームを混ぜて 1 つに持つ。ID は全体で一意なので、どちらの集まりから引くかは ID だけで決まり、列を分ける理由がない。順序は持たない (並びは Tier と ID から決まる)。直列の会話では常に空である。

定義そのものはデータベースに持たない。置き場は設定の探索パスから決まる派生物であり、保存すると設定を変えたときに食い違う — #903215 で作業ディレクトリについて下した判断と同じである。

**メッセージ** の変更はこの文書では扱わない。宛先と内訳の列は [#640275](2026-09-08-team-session-mentions-%23640275.md) が決める。

### インターフェース

**会話の作成** — 既存の作成に種類を足す。種類がチームなら、規定エージェントを 1 体だけ有効にした状態の会話を返す。

**名簿** — 1 つの会話について、有効なものと、まだ有効でないものを一度に返す。各項目は `agent.Agent` としての内容に加えて、共通かチームかの由来を持つ。2 回問い合わせる形にすると、片方だけ古い一覧を描く瞬間が生まれる。読めなかった定義は、何が読めなかったかの一覧として同じ応答に載せる。

**有効化と解除** — 名簿へ入れる / 外す。誰でも外せて、名簿が空になることも許す。定義そのものには触れない。会話の途中で外しても、その相手の過去の発言は消えない。消すと、残っているメッセージの送り手が誰なのか分からなくなる。

**定義の作成** — 会話の下に置く。「定義を作る」と「この会話で有効にする」を 1 度に行う操作だからである。共通の定義に対する既存の操作と同じ入力を取り、検証も同じものを通す。

**定義の編集と削除** — 会話の下に置かない。**共有物への操作であり、別の会話から同じファイルを書けることが経路から読めなければならない。** 削除は定義を消すだけで、過去の発言にもチケットにも触れない。有効にしていた会話の名簿からも掃除しない — 「定義が見つかりません」と出るほうが、黙って人が減るよりよい。

**コピー** — 共通エージェントを 1 体指定すると、その内容でチームの定義を作る。ID は元と同じでは作れないので、衝突しないものを自動で選ぶ。コピー後は元と縁が切れる。以後どちらを直しても、もう片方は変わらない。

**削除の波及** — 会話を消しても、チームの定義は消さない。ほかの会話が同じ定義を使っている。

### 会話ごとの定義からの移行

初版で作られた `<data_dir>/sessions/<ID>/agents/*.json` は、起動時に 1 度だけ共有の置き場へ移す。

- **ファイル名だけで列挙し、中身は解析しない。** ID はファイル名から決まる。解析すると、壊れた定義がその会話に取り残されて誰にも読めなくなる。
- 名前が衝突したら `-2`, `-3`, … を付ける。
- 移した ID は、その会話で有効なままにする。移す前に使えていたものが、移したあとに居なくなってはならない。
- **改名した会話では、過去の発言とチケットの担当も同時に書き換える。** やらないと、`@reviewer` が別人になった会話で、過去の吹き出しと担当チケットが新しい `reviewer` の名前と色で描かれる。
- やり直さないための印は置かない。古いディレクトリが無いこと自体が記録になり、自然に 2 度目は何もしない。

### 処理フロー

**チームセッションを作る。** 左パネルの「新しい会話」の右の ∨ を押すと、「チームセッション」が出る。選ぶと会話が作られ、規定エージェントが 1 体だけ居る状態で開く。右パネルが開いており、そこから人を足す。

**人を足す。** 共通の欄で「参加」、チームの欄で「有効化」を押すと名簿に入る。「チームへコピー」を押すとチームの欄へ写しが作られる。チームの欄の「＋」は空の定義から作る。いずれも保存の検証は共通のものと同じで、失敗した項目が分かる形で返る。

**人を外す。** メンバーの欄で「外す」。誰でも外せる。定義は残るので、あとで有効にし直せる。

**定義を直す・消す。** チームの欄から行う。**共有物なので、直せば有効にしている全ての会話に効き、消せば全ての会話から居なくなる。** そのことを欄の説明と削除の確認に明記する。いままで黙って 1 会話にしか効かなかったものが、黙って全部に効くようになるので、そこは黙ってはいけない。

**異常時。** 定義のファイルが壊れている場合、その 1 体だけが名簿に載らず、読み込みの失敗として画面に出る — 共通の定義に対する既存の扱い (`agent.Set.Errors`) と同じである。会話そのものは開けて読める。名簿が空になった場合 (全員外れた・全部壊れた) は、送信を止め、理由を帯に出す。

### 画面

**左パネル。** 「新しい会話」のボタンの右端を細く区切り、∨ を置く。押すと下に「チームセッション」が 1 行出る。既定の動作 (ボタン本体を押す) は今までどおり直列の会話で、チームは 1 手増える位置に置く。日常的に使うのは直列の会話のほうだからである。一覧の各行には、チームであることが分かる印を出す。エージェント名を出している位置に、代わりに人数を出す — チームには「担当エージェント」が 1 人ではないので、そこに 1 つの名前を出すと嘘になる。

**右パネル。** チームセッションを開いているときだけ出る。上から順に、この会話のメンバー / 共通エージェント / チームエージェント / チケット ([#189542](2026-09-08-team-session-tickets-%23189542.md)) の 4 つの欄を積む。それぞれ折りたためる。

**有効なものは由来を問わず 1 つの欄にまとめる。** 「@ を打つと誰が出るのか」に、画面の 1 か所が答えられるようにするためである。由来で割ると 2 か所を見て頭の中で合成することになり、並びもメンションの補完と一致しない。由来は行に印として添える。

下の 2 つの欄は、まだ有効でないものを由来ごとに並べる。共通とチームでは行える操作が違う (共通の定義を直すのは設定画面の仕事) ので、欄も分かれる。有効になっているチームエージェントは、メンバーの欄とチームの欄の両方に出る — 共有物の編集と削除が、有効かどうかで行えたり行えなかったりするのは筋が通らない。

各行には Tier を出す。誰に何を頼めるかがその数だけで決まるからである (#640275)。

パネルは開閉でき、幅も変えられる。会話の幅を常に削るには、ここに出るものは参照のためのものが多すぎるので、既定は左の一覧と同程度に留める。

幅を変えられるようにするのは、ここに出るものの長さが会話ごとに違うためである。題の長いチケットが並ぶ会話もあれば、名前の短い担当が数人だけの会話もある。決め打ちの幅は、足りないか余るかのどちらかにしかならない。

選んだ幅は覚えておく。開き直すたびに戻るなら、変えられないのとほとんど同じである。掴む操作しか用意しないのも同じ理由で駄目で、焦点を置いて矢印でも変えられるようにする。

## テスト方針

- 会話の種類がチームのとき、作業ディレクトリが `team/<ID>` 以下になり、直列のときは従来どおり `series/<ID>` になること。
- 既存の (種類を持たない) 会話が直列として読まれ、作業ディレクトリも表示も変わらないこと。
- チームの定義が、共通と同じ検証を通ること。ID の重複とモデル未指定が同じ理由で断られること。
- Tier 0 が、共通では断られ、チームでは通ること。ファイルへ書いた 0 が 0 のまま読み戻せること。同じ値を共通の探索パスから読んだときは 1 へ引き上げられること。
- チームの置き場の定義が、共通の一覧には出ないこと。共通の走査が `team/` を掘らないこと。
- 規定エージェントをコピーした写しが、Tier 0 のまま、規定エージェント扱いではない状態で名簿に載ること。
- 共通に既にある ID でチームの定義を作ろうとすると断られること。**別の会話からでも、同じ ID をもう一度は作れないこと。**
- 作った定義が、別のチーム会話からも有効にできること。**直すと、有効にしている全ての会話に効くこと。**
- 消すと、有効にしていた全ての会話から居なくなり、何が消えたのかが名簿の失敗として出ること。
- 会話を消しても、チームの定義が残り、ほかの会話から使えたままであること。
- 規定エージェントを外せること。名簿が空になっても、開いて読めること。
- 定義を 1 つ壊した状態で会話を開くと、残りの名簿が読め、壊れた 1 件が失敗として出ること。
- **移行を本物の形で試す** — 会話ごとの定義を 2 つの会話に置き、片方の ID を衝突させ、発言とチケットを持たせた状態で起動する。移動・改名・有効なままであること・過去の ID の書き換え・2 度目の起動で何も起きないことを確かめる。

手で確かめるのは、左パネルの ∨ の開閉と、右パネルの 4 つの欄の折りたたみ、そして幅を詰めたときに会話が読める幅を保てているか。

## 実行と画面の切り離し

**実行は、それを見ている画面の寿命から切り離す。**

もとは 1 回の実行が送信の HTTP リクエストそのものに乗っていた。経過を返す経路と実行の寿命が同じものだったので、ブラウザを更新した瞬間に要求の文脈が切れ、走っていた生成ごと止まっていた。書きかけのファイルも、承認待ちの手番も、そこで捨てられる。チームでは 1 ラウンドが何十手番にもなるので、これは実際に困る。

実行は自分の寿命で走らせ、経過は会話ごとの中継へ流す。画面はいつでも繋ぎ直せる。見ている者が居なくなっても実行は続き、戻ってくればその続きから見える。止まるのは利用者が止めたときだけである。

**繋ぎ直したときは、それまでの経過を流し直す。** 画面は開いた時点で履歴を読み、そこへ経過を重ねる。同じ経過が 2 度届いても壊れないよう、発言・道具の呼び出し・メッセージは識別子で見分け、押し直すのではなく組み立て直す。

中継が覚えておく経過には上限を置く。長い生成では字が数万件になるためで、溢れたら中身のある出来事を残して字だけを捨てる。捨てた分は画面の側で埋まる — **実行が終わったところで必ず履歴を読み直す**からである。流れてくる経過は「いま動いている」を伝えるためのもので、正しいのは常にデータベースのほうである。

**どの会話が走っているかは、会話の応答に載せる。** 画面はそれを見て、開いた時点で繋ぎ直し、一覧にも印を出す。開いてはじめて分かる形だと、更新したあとどれが動いているのかを探すことになる。

## リスクと未決事項

- **共有になったことによる巻き添え。** 定義を直すと、それを有効にしている全ての会話に効く。走っている会話の途中でも効く。明記はするが、止める仕組みは置いていない — 止めるには会話ごとの写しへ戻すことになり、それは撤回した案である。
- **チームの定義と探索パスの変更。** 置き場は `agent_paths[0]` の下なので、設定でそこを変えるとチームの定義は読めなくなる。名簿は「定義が見つかりません」を出し、会話そのものは開けて読める。
- **名簿の人数の上限を置くか。** 置いていない。指示文へ載る名簿と宛先の候補が太るだけで、実行を壊すものではない。実際に何体まで使い物になるかは回してみないと分からない。
- **提供元が黙ったままになることがある。** 生成そのものには時間の上限を置かず、何も届かない時間だけを見張る (既定 5 分)。時間で切ると長い仕事ができなくなるためで、伸びるのはモデルが考えている間ではなく通路が死んでいる間である。上限に達したら失敗として伝える — 黙って終わったことにすると、画面には答え終わったように見える。読み込みの長いモデルではこの上限に当たりうるので、設定で延ばせるようにしてある。
- **実行を切り離したので、閉じても止まらない。** ブラウザを閉じても、走っているものは走り切る。それが望ましい場面 (長い作業) と、そうでない場面 (誤って始めた) の両方がある。止める手段は `/stop` と中断ボタンのままで、開き直してから止めることになる。
- **繋ぎ直しは、それまでの経過を流し直す。** 長い実行のあとに繋ぎ直すと、その分がまとめて流れる。上限で削っているので詰まりはしないが、届くまでに間がある。
