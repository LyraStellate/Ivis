## 背景と課題

[全体設計 #258413](2026-09-08-team-session-overview-%23258413.md) の一部。会話は 1 体のエージェントとしか結び付けられず (`store.Session.AgentID`)、複数体が居る会話という入れ物が無い。エージェントの定義も共通の探索パス (`config.AgentPaths`) にあるものだけで、「この仕事のためだけの担当」を作ると全ての会話の一覧に並び続ける。

## ゴール / 非ゴール

### ゴール

- チームセッションを作れる。作業ディレクトリは会話ごとに分かれ、直列の会話と混ざらない。
- そのセッションにだけ存在するエージェントを作成・編集・削除できる。
- 共通のエージェントを、そのチームに参加させられる。ここだけ変えたいときはコピーして固有にできる。
- 誰が居るかが右パネルで一覧でき、宛先の無い発言が誰に届くかが分かる。

### 非ゴール

- **メンバーごとの作業ディレクトリ。**
- **チーム構成の雛形化・書き出し・取り込み。**
- **共通エージェントの編集をこの画面から行うこと。** 共通の定義を直すのは設定画面の仕事で、ここは参加とコピーだけを扱う。2 か所から同じファイルを書けるようにすると、どちらで直したか分からなくなる。
- **チームセッションから直列への変換、およびその逆。**

## 設計案

### 採用案

**会話に種類を足す。** セッションは「直列 (series)」か「チーム (team)」のどちらかである。既存の会話は全て直列とする。種類は作成時に決まり、後から変わらない。

出自 (`Source`: web / discord) とは別の軸として持つ。出自は「どこから来た会話か」、種類は「どう進む会話か」であり、混ぜると Discord から来た会話をチームにできるかという問いに答えられなくなる (答えは「できない」で、それは出自の側の制約である)。

**作業ディレクトリは `<作業ディレクトリ>/team/<セッション ID>/`。** #903215 が `series` という段を挟んでおいたのは、まさにこのためである。`config.SessionWorkspace` が種類を見て段を選ぶようにする。メンバーは全員この 1 つを共有する。1 つの仕事を分担しているのだから、成果物の置き場を分ける理由がない。

**メンバーは 2 種類の由来を持つ 1 つの名簿である。**

- **参加している共通エージェント** — `config.AgentPaths` にある定義への参照。定義を直せば、参加している全てのチームに効く。
- **セッション固有エージェント** — その会話のためだけの定義。作った会話の中にしか存在しない。

名簿の中では両者を区別しない。並びは既存の `sortIDs` と同じく Tier 順、同 Tier では ID 順とする。上位から下位へ読める並びは、そのまま指示の流れの向きである。

**セッション固有の定義もファイルに置く。** 置き場は `<data_dir>/sessions/<セッション ID>/agents/<ID>.json` とし、形式・検証・読み込みは共通のものと全く同じにする。「エージェント定義はファイルが正」という #528664 の原則をここで折らない。同じ `agent.Agent` として読めるので、指示文の組み立ても、ツールの許可判定も、画面の編集フォームも、共通のものがそのまま使える。

**ID はセッションの中で一意。** 共通に既にある ID と同じものは、そのセッションでは作れない。名簿の外では衝突してよい (別のチームが同じ名前の担当を持つのは自然である)。一意性をセッション内に閉じるのは、メンションの宛先が ID だからである。同じ会話に同じ名前が 2 つあると、`@reviewer` が誰を指すのか決められない。

**セッション固有の定義は Tier 0 を持てる。** 共通の一覧で Tier 0 を規定エージェントだけに絞っているのは、会話の入口が 2 つある状態を定義の書き換えで作れないようにするためだった ([#528664](2026-09-04-agent-system-%23528664.md))。チームの入口は窓口として会話が明示して持つので、そこへ同じ制限を掛ける理由がない。対等な 2 人組は正当な構成であり、同位どうしは依頼しかできないという規則 ([#640275](2026-09-08-team-session-mentions-%23640275.md)) がそれを支える。

この違いは検証の側だけに置く。定義の読み書きは共通と同じ経路を通り、共通の一覧を組むところで Tier 0 を引き上げる。読む側に制限を置くと、ファイルに書いた値と読める値が食い違い、どちらが正か決められなくなる。

**窓口を 1 体決める。** 既存の `Session.AgentID` をそのまま使う。宛先の書かれていない利用者の発言と、`@*` はここへ届く。既存の入力欄のエージェント選択が、そのまま窓口の切り替えになる。新しい概念を足さずに済み、直列の会話での意味 (「この会話で答える人」) とも食い違わない。

**窓口は名簿の中から選ぶ。** 直列の会話では共通の一覧から選ぶが、チームでは名簿から選ぶ。共通の一覧だけを見ると、その会話のために作った固有のエージェントを窓口にできない。窓口を移せなければ、いまの窓口も外せない (外すと宛先の無い発言の行き先が消えるため) ので、名簿は最初に置かれた規定エージェントに縛られたままになる。

入力欄のエージェント選択も、チームでは名簿を出す。共通の一覧を出すと、この会話に居ない相手を窓口にしようとして断られる。

**チームは 1 体から始まる。** 作成時に規定エージェント (`status.default_agent`) を参加させ、それを窓口にする。空のチームから始めると、最初の発言の行き先が無く、画面は「誰も居ません」としか言えない。

### 検討した代替案

- **セッション固有の定義をデータベースへ持つ。** セッションを消せば外部キーで一緒に消え、後始末が要らない。だが定義を読む経路が 2 つになり、`agent.Set` の読み込み・検証・重複判定を書き写すことになる。ファイルに置けばその全部が既存のまま効く。後始末は自分で書くほうが安い。
- **共通エージェントはコピーしたものだけが参加できる。** チームが自己完結し、共通の定義を後から直しても過去のチームは変わらない (再現性は高い)。だが同じ定義の写しがセッションの数だけ増え、指示文の誤りを直しても既存のチームには伝わらない。直しが伝わらないことのほうが、日々の使い勝手を損なう。コピーは「ここだけ変えたい」ときの手段として残す。
- **チームのメンバーを共通エージェント全部にする (参加という概念を持たない)。** 名簿を持たずに済むが、宛先の候補が手元の全定義になり、増やすほど選べなくなる。指示文へ載せる名簿も同じだけ太る。チームは「選んで組む」ものである。
- **窓口を持たず、宛先の無い発言を Tier のいちばん上へ届ける。** 決め事が減るが、同位が 2 体居るチームで宛先が決まらない。窓口を明示すれば、利用者から見て「誰に話しかけているか」が常に 1 つに定まる。
- **会話の種類を出自 (`Source`) の値として足す (`team` という出自を作る)。** 列を増やさずに済むが、「Discord から来たチーム」を表せない — 表せないこと自体は今回の非ゴールと一致するものの、将来それを許すときに出自と種類をほどく作業が発生する。最初から別の軸にしておく。

## 詳細設計

### データモデル

**セッション** に 2 つ足す。

- **種類。** 直列かチームか。既存の行は直列として読む。作成時に決まり、更新の対象にしない。
- **参加している共通エージェントの ID の一覧。** 順序は持たない (並びは Tier と ID から決まる)。直列の会話では常に空である。

セッション固有の定義そのものはデータベースに持たない。置き場はセッション ID から一意に決まる派生物であり、保存すると `data_dir` を変えたときに食い違う — #903215 で作業ディレクトリについて下した判断と同じである。

**メッセージ** の変更はこの文書では扱わない。宛先と内訳の列は [#640275](2026-09-08-team-session-mentions-%23640275.md) が決める。

### インターフェース

**会話の作成** — 既存の作成に種類を足す。種類がチームなら、指定されたエージェント (省略時は規定エージェント) を最初の参加者かつ窓口として、その状態の会話を返す。

**メンバーの一覧** — 1 つの会話について、名簿を返す。各項目は `agent.Agent` としての内容に加えて、共通か固有かの区別を持つ。画面は共通の欄と固有の欄に振り分けてこれを描く。同じ経路で、参加していない共通エージェント (コピー元および参加候補) も返す。2 回問い合わせる形にすると、片方だけ古い一覧を描く瞬間が生まれる。

**参加と離脱** — 共通エージェントを名簿へ入れる / 外す。窓口を外すことはできない。外すなら先に窓口を移す。会話の途中で外しても、その相手の過去の発言は消えない。消すと、残っているメッセージの送り手が誰なのか分からなくなる。

**固有エージェントの作成・更新・削除** — 共通の定義に対する既存の操作 (`POST /api/agents` ほか) と同じ入力を取り、書き先だけがセッションの下になる。検証も同じものを通す。削除は定義を消すだけで、そのエージェントの過去の発言には触れない。

**コピー** — 共通エージェントを 1 体指定すると、その内容で固有の定義を作る。ID は元と同じでは作れないので (共通と衝突するため)、衝突しないものを既定として提案し、利用者が変えられるようにする。コピー後は元と縁が切れる。以後どちらを直しても、もう片方は変わらない。

**削除の波及** — 会話を消すと、その会話の固有エージェントの定義も消える。定義はその会話のために作られたもので、会話が無くなれば読み手が居ない。作業ディレクトリを消さないこと (#903215 の非ゴール) とは扱いが違う — あちらは利用者が置いた材料と成果物であり、こちらは会話の一部である。

### 処理フロー

**チームセッションを作る。** 左パネルの「新しい会話」の右の ∨ を押すと、「チームセッション」が出る。選ぶと会話が作られ、規定エージェントが 1 体だけ居る状態で開く。右パネルが開いており、そこから人を足す。

**人を足す。** 右パネルの共通の欄で「参加」を押すと名簿に入る。「コピー」を押すと固有の欄へ写しが作られ、その場で編集フォームが開く。固有の欄の「＋」は空の定義から作る。いずれも保存の検証は共通のものと同じで、失敗した項目が分かる形で返る。

**人を外す。** 共通は「参加を外す」、固有は削除。どちらも窓口には行えない。窓口を移してから行う。

**異常時。** 固有エージェントのファイルが壊れている場合、その 1 体だけが名簿に載らず、読み込みの失敗として画面に出る — 共通の定義に対する既存の扱い (`agent.Set.Errors`) と同じである。会話そのものは開けて読める。名簿が空になった場合 (全員外れた・全部壊れた) は、送信を止め、理由を入力欄に出す。

### 画面

**左パネル。** 「新しい会話」のボタンの右端を細く区切り、∨ を置く。押すと下に「チームセッション」が 1 行出る。既定の動作 (ボタン本体を押す) は今までどおり直列の会話で、チームは 1 手増える位置に置く。日常的に使うのは直列の会話のほうだからである。一覧の各行には、チームであることが分かる印を出す。エージェント名を出している位置に、代わりに人数を出す — チームには「担当エージェント」が 1 人ではないので、そこに 1 つの名前を出すと嘘になる。

**右パネル。** チームセッションを開いているときだけ出る。上から順に、共通エージェント / 固有エージェント / チケット ([#189542](2026-09-08-team-session-tickets-%23189542.md)) の 3 つの欄を積む。それぞれ折りたためる。共通の欄では参加中のものを上に、参加していないものを下に置く。各行には Tier と、窓口かどうかを出す。Tier を出すのは、誰に何を頼めるかがその数だけで決まるからである (#640275)。

パネルは開閉でき、幅も変えられる。会話の幅を常に削るには、ここに出るものは参照のためのものが多すぎるので、既定は左の一覧と同程度に留める。

幅を変えられるようにするのは、ここに出るものの長さが会話ごとに違うためである。題の長いチケットが並ぶ会話もあれば、名前の短い担当が数人だけの会話もある。決め打ちの幅は、足りないか余るかのどちらかにしかならない。

選んだ幅は覚えておく。開き直すたびに戻るなら、変えられないのとほとんど同じである。掴む操作しか用意しないのも同じ理由で駄目で、焦点を置いて矢印でも変えられるようにする。

## テスト方針

- 会話の種類がチームのとき、作業ディレクトリが `team/<ID>` 以下になり、直列のときは従来どおり `series/<ID>` になること。
- 既存の (種類を持たない) 会話が直列として読まれ、作業ディレクトリも表示も変わらないこと。
- セッション固有の定義が、共通と同じ検証を通ること。ID の重複とモデル未指定が同じ理由で断られること。
- Tier 0 が、共通では断られ、セッション固有では通ること。ファイルへ書いた 0 が 0 のまま読み戻せること。同じファイルを共通の探索パスから読んだときは 1 へ引き上げられること。
- 規定エージェントをコピーした写しが、Tier 0 のまま、規定エージェント扱いではない状態で名簿に載ること。
- 共通に既にある ID で固有を作ろうとすると断られること。別のセッションでなら同じ ID を作れること。
- コピーした定義が元と独立していること — 元を直しても写しが変わらず、その逆も同じ。
- 窓口を外そうとすると断られること。窓口を移してからなら外せること。
- 固有のエージェントを窓口にできること。名簿に居ない相手は窓口にできないこと。直列の会話では今までどおり共通の一覧から選ばれること。
- 規定エージェントが窓口でなくなれば、名簿から外せること。
- 会話を消すと固有の定義のディレクトリが消え、作業ディレクトリは残ること。
- 固有の定義を 1 つ壊した状態で会話を開くと、残りの名簿が読め、壊れた 1 件が失敗として出ること。

手で確かめるのは、左パネルの ∨ の開閉と、右パネルの 3 つの欄の折りたたみ、そして幅を詰めたときに会話が読める幅を保てているか。

## 実行と画面の切り離し

**実行は、それを見ている画面の寿命から切り離す。**

もとは 1 回の実行が送信の HTTP リクエストそのものに乗っていた。経過を返す経路と実行の寿命が同じものだったので、ブラウザを更新した瞬間に要求の文脈が切れ、走っていた生成ごと止まっていた。書きかけのファイルも、承認待ちの手番も、そこで捨てられる。チームでは 1 ラウンドが何十手番にもなるので、これは実際に困る。

実行は自分の寿命で走らせ、経過は会話ごとの中継へ流す。画面はいつでも繋ぎ直せる。見ている者が居なくなっても実行は続き、戻ってくればその続きから見える。止まるのは利用者が止めたときだけである。

**繋ぎ直したときは、それまでの経過を流し直す。** 画面は開いた時点で履歴を読み、そこへ経過を重ねる。同じ経過が 2 度届いても壊れないよう、発言・道具の呼び出し・メッセージは識別子で見分け、押し直すのではなく組み立て直す。

中継が覚えておく経過には上限を置く。長い生成では字が数万件になるためで、溢れたら中身のある出来事を残して字だけを捨てる。捨てた分は画面の側で埋まる — **実行が終わったところで必ず履歴を読み直す**からである。流れてくる経過は「いま動いている」を伝えるためのもので、正しいのは常にデータベースのほうである。

**どの会話が走っているかは、会話の応答に載せる。** 画面はそれを見て、開いた時点で繋ぎ直し、一覧にも印を出す。開いてはじめて分かる形だと、更新したあとどれが動いているのかを探すことになる。

## リスクと未決事項

- **窓口の移動と手番の関係。** 生成中に窓口を変えられると、走っている手番の宛先解決が途中で変わる。直列の会話では生成中はエージェントを変えられない (`Composer` が `busy` で無効化する) ので、同じ扱いにする。
- **固有エージェントの置き場と `data_dir` の変更。** 設定で `data_dir` を変えると、それまでの固有定義は読めなくなる。履歴データベースも同じ場所にあるので会話ごと見えなくなり、食い違いは起きない。だが「会話は見えるのに担当だけ居ない」状態が作れないことは確かめる。
- **名簿の人数の上限を置くか。** 置いていない。指示文へ載る名簿と宛先の候補が太るだけで、実行を壊すものではない。実際に何体まで使い物になるかは回してみないと分からない。
- **実行を切り離したので、閉じても止まらない。** ブラウザを閉じても、走っているものは走り切る。それが望ましい場面 (長い作業) と、そうでない場面 (誤って始めた) の両方がある。止める手段は `/stop` と中断ボタンのままで、開き直してから止めることになる。
- **繋ぎ直しは、それまでの経過を流し直す。** 長い実行のあとに繋ぎ直すと、その分がまとめて流れる。上限で削っているので詰まりはしないが、届くまでに間がある。
