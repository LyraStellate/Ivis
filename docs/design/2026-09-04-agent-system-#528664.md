## 背景と課題

[全体設計 #312078](2026-09-04-agent-expansion-overview-%23312078.md) の一部。エージェントを増やす手段が JSON の手書きしかなく、委譲先も各定義に列挙する形になっている。

現状の具体的な引っかかりは次のとおり。

- `internal/agent/agent.go` の `Delegates` は呼べる相手の ID 列。N 体いると最悪 N×N 行の記述になる。しかも循環は `internal/engine/exec.go` が `parent.stack` を辿る実行時検査でしか防げず、定義を見ただけでは安全か分からない。
- 話し手の色は ID のハッシュから 8 色へ機械的に割り当てる (`web/src/lib/who.js`)。よく使う 2 体が同じ色に落ちても直せない。
- 委譲された子は毎回まっさらな文脈で始まる (`exec.go` が `runCtx` を依頼文 1 件だけで初期化する)。同じ子を繰り返し呼ぶ会話では、毎回同じ前提を説明し直すことになる。
- モデル側の推論 (thinking) を使う手段がない。生成パラメータに手で書けても、そのモデルが対応しているかは試すまで分からない。
- セッションのエージェント選択は画面右上の `select` (`web/src/lib/ChatView.svelte`)。会話の主体を決める操作が隅にあり、モデル名の表示と並んで上端の情報量を上げている。

## ゴール / 非ゴール

### ゴール

- 設定窓からエージェント設定へ入り、作成・編集・複製・削除ができる。結果は定義ファイルに残る。
- 委譲の可否を Tier で表し、`delegates` を廃止する。
- 規定エージェントが常に 1 体存在し、削除できない。
- 記憶 (委譲時の引き継ぎ)・推論・色をエージェントごとに決められる。
- エージェントの一覧が自動でシステムプロンプトに載り、委譲先を選ぶ材料になる。
- エージェント選択が入力欄に移り、切り替えても会話は続く。

### 非ゴール

- **Tier ごとの権限プリセット。** ツールとスキルの許可は今までどおり定義ごとに書く。Tier が決めるのは委譲の向きだけ。
- **Tier0 を複数持つこと。** 入口は 1 つに保つ。
- **手書き JSON のコメント・整形の保存。** 保存時に失われる。
- **定義ファイルの外部変更の即時反映。** 取り込む手段は既存の再読み込みのまま。

## 設計案

### 採用案

3 つの決定からなる。

**1. 書き戻しを解禁する。** 「定義ファイルが正」は維持する — 読み込みは常にファイルからで、Ivis はファイルの内容を超えた状態を持たない。変えるのは、書き手が Ivis にもなりうるという点だけである。保存時は定義全体を JSON として書き直す。

**2. 委譲を Tier で表す。** 各エージェントは非負整数の tier を持ち、委譲できるのは tier が真に大きい相手だけとする。数字が小さいほど上位で、下位は上位を呼べない。同じ Tier どうしも呼べない。

これで、誰が誰を呼べるかは各定義の tier だけで決まる。エージェントを 1 体足すとき、既存の定義には触らない。循環は tier が単調に増える以上、構造的に起こりえない。

**3. 一覧をシステムプロンプトへ載せる。** 自分より下位のエージェントの ID・表示名・tier・説明を、生成のたびに定義群から組み立てて指示文へ添える。モデルはこれを見て委譲先を選ぶ。したがって説明文は「何ができるか」ではなく「どういうときに呼ぶか」を書く欄として扱い、画面でもそう案内する。

### 検討した代替案

- **保存先を分ける (利用者が置いた探索パスは読み取り専用、Ivis 管理下だけ編集可)。** 原則を崩さずに済むが、利用者は自分が作った定義の一部だけが画面から直せない理由を理解できない。どちらに置いたかを覚えていないと編集できるかも分からず、実質「編集できないことがある」という仕様になる。
- **一覧を派生ファイルとして書き出す。** 当初の要求はこの形だったが採らない。一覧は定義群から一意に決まる派生物であり、ファイルにすると定義と一覧が食い違ったときにどちらが正か決められなくなる。しかも食い違いは必ず起きる (ファイルを手で消した、外から定義を足した、書き出しの途中で落ちた)。定義から毎回組み直せば、その状態自体が存在しない。利用者が一覧を確かめる用途は管理画面が担う。
- **`delegates` を残して Tier と併用する。** 移行は滑らかになるが、呼べるかどうかの判断が 2 か所に分かれ、「一覧には出るのに呼べない」といった説明しづらい状態を生む。
- **Tier を上限だけの制約にする (同 Tier も呼べる)。** 横の連携ができるようになるが、同 Tier どうしで循環しうるため実行時の循環検出を残すことになり、Tier を入れる利点の半分が消える。
- **色を任意の色指定にする。** 自由度は上がるが、画面の配色と調和しない色を選べてしまう。既にある 8 色から選ぶ形にする。

## 詳細設計

### データモデル

エージェント定義に加える項目。

- **tier** — 非負整数。委譲の可否を決める唯一の材料。省略時は 1 とみなす (規定より下)。0 は規定エージェントだけが持てる。
- **記憶** — 真偽。委譲されたときに、同じセッション内での前回のやり取りを引き継ぐか。省略時は引き継がない (現状の挙動)。
- **推論** — 真偽。モデルの推論機能を使うか。省略時は使わない。
- **色** — 用意された 8 色のいずれかの名前、または空。空なら現状どおり ID から機械的に決める。

削除する項目。

- **delegates** — 読み込み時に無視する。残っていても読み込みエラーにはしない。手元の定義が一斉に読めなくなる事態を避けるため。

規定エージェントは、他と同じく探索パス上の JSON ファイルとして存在する。他と違うのは次の 3 点だけ。ID が固定されていること、tier が常に 0 で画面からもファイルからも変えられないこと (ファイルに他の値が書いてあれば 0 として読む)、削除を拒むこと。ファイルが直接消されていた場合は起動時に既定値で作り直す。それ以外の項目 — 表示名・説明・モデル・指示文・ツール・スキル・記憶・推論・色 — は変更できる。

会話履歴の持ち方は変えない。エージェントを切り替えたときの引き継ぎは、セッションが 1 本の履歴を持ち続けることで既に満たされている。

推論の出力は本文と分けて保存する。混ぜると、後から読み返したときに結論と過程の区別がつかなくなる。

### インターフェース

一覧の取得に加えて、作成・更新・削除を設ける。

- **作成** — ID・表示名・説明・モデル・指示文・tier・ツール・スキル・記憶・推論・色を受け取る。ID はファイル名になるため、区切り文字や親ディレクトリ参照を含むものは断る。既存と重複する ID、tier に 0、モデル未指定も断る。保存先は探索パスの先頭。
- **更新** — 既存の読み込み元ファイルへ書き戻す。ID は変えられない。ID はファイル名から導出するため、変更はファイルの移動になる。複製して古い方を消す導線で足りる。規定エージェントは tier の変更だけ断り、他は通す。
- **削除** — 規定エージェントは断る。他は読み込み元ファイルを消す。そのエージェントを使っているセッションは残す。v1 と同じく「開けるが続行できない」扱いになる。
- **複製** — 作成の一形態。元の内容に新しい ID だけを受け取る。

いずれも成功したら定義を読み直し、一覧を組み直す。失敗の理由は種類ごとに分け、画面が「ID を変えてください」「モデルを選んでください」と具体的に言えるようにする。まとめて「保存できません」にすると、利用者はどこを直せばよいか分からない。

委譲ツールは、呼べる相手を tier の比較で判定する。不許可のときは実行を失敗させず、「その相手は自分より上位のため呼べません」という結果をモデルへ返す。ツールが許可されていない場合と同じ扱いで、モデルが別の手を考えられるようにする。

生成要求に「推論を使うか」を足す。対応していないモデルへ推論を求めたときの失敗は、接続不可やモデル未取得と同じく種類を分けて扱い、画面が「このモデルは推論に対応していません」と示せるようにする。

### 処理フロー

**保存** — 入力を検証し、一時ファイルへ書いてから置き換える。書き込みの途中で落ちても壊れた JSON が残らないようにするため。置き換えたら定義を読み直す。読み直しに失敗した場合、つまり書いた内容が自分で読めない場合は、その事実を返す。

**委譲** — 呼び出し側の tier と相手の tier を比べ、相手が上位または同位なら断る。通ったら、記憶が有効な場合に限り、同じセッション内でその相手が過去に委譲されたときのやり取りを入力の先頭へ置く。無効なら今までどおり依頼文だけで始める。

深さの上限は残す。tier は単調に増えるので無限には深くならないが、tier を大きく飛ばせば依然として深くなりうる。

**エージェントの切り替え** — 入力欄で選び直すと、セッションが持つエージェント ID が変わる。履歴はそのまま次のエージェントへ渡る。誰の発言かは各発言が持つエージェント ID と色で区別できるので、履歴の見え方は変えない。

**一覧の組み立て** — 生成のたびに、自分より tier の大きいエージェントを tier 順・ID 順に並べ、ID・表示名・tier・説明を指示文へ添える。説明が空のものは説明が無いと分かる形で並べる。呼べる相手が 1 体もいなければ何も添えない。

### 画面

設定窓に「エージェント設定」の項目を置く。押すと同じ窓がエージェント設定へ切り替わる。別の窓を開くと、どちらが手前かを利用者が管理することになるため、窓は 1 つのままにして上端に戻る導線を置く。

エージェント設定は左に一覧、右に編集フォーム。一覧は tier 順に並べ、各行に色・表示名・tier・モデルを出す。規定エージェントには、削除できないことが分かる印を付ける。

フォームは上から、名前と説明、tier、モデル、指示文、ツールとスキル、記憶と推論、色。説明の欄には「どういうときにこのエージェントを呼ぶか」を書く欄だと分かる案内を添える。ここに書いた文がそのまま上位エージェントの判断材料になるため、書き方が結果を左右する。

チャット画面の右上からエージェント選択とモデル名を外す。エージェントは入力欄で選ぶ。モデル名は編集の対象ではないので、選択肢の中に添える形にする。

## テスト方針

- **Tier による委譲の可否**を、上位から下位・下位から上位・同位・自分自身の各組み合わせで検証する。ここが誤ると権限の壁が壊れるため最も厚くする。
- **規定エージェント**が削除を拒み、tier の変更を受け付けず、ファイルが無い状態から作り直されることを検証する。
- **保存**について、不正な ID・重複した ID・モデル未指定・tier に 0 の指定が断られること、および保存後に読み直せることを検証する。
- **記憶**が有効なときに前回のやり取りが子の入力へ入り、無効なときに入らないことを、プロバイダのモックで検証する。
- **既存定義との互換**として、`delegates` を持つ定義と tier を持たない定義が読み込めることを検証する。
- **手動確認** — 推論に対応するモデルと対応しないモデルの双方で、推論を有効にしたときの表示と失敗の伝わり方。エージェントを増やしたときにシステムプロンプトの一覧が意図どおり絞られること。

## リスクと未決事項

- **手書きの内容が失われる。** 書き戻しは JSON を丸ごと書き直すため、コメントや項目の並び順は保存時に消える。保存前に警告を出すかどうかは、実際に困る場面が出てから決める。
- **推論の出力を次のターンへ渡すか。** 保存して折りたたんで見せるところまでは決めているが、次の入力に含めるかは決めていない。含めないと過程が切れる場面があり、含めると文脈を大きく食う。実際のモデルで試してから決める。
- **記憶の量に上限が要るか。** 引き継ぎを有効にしたまま長い会話を続けると、子へ渡す入力が際限なく伸びる。上限の置き方は、[#903215](2026-09-04-session-runtime-%23903215.md) で文脈使用量が見えるようになってから決める。
- **tier の向きが利用者に伝わるか。** 数字が小さいほど上位という向きは直感に反することがある。画面の言い回しで補えるかは、実際に使って確かめる。
