## 背景と課題

基盤設計 (#694381) では画面を「チャット本体と左パネル」とだけ定め、内部の作りには踏み込まなかった。
最初の実装は動くところまで到達したが、次の 3 つの問題を抱えている。いずれも配色の調整では
解消しない。

**描画経路が 2 本ある。** `web/src/App.svelte` は確定した履歴を持つ `messages` と、生成中だけの
`live` という 2 つの配列を持ち、`web/src/lib/Chat.svelte` の `shown` が
`live.length > 0 ? live : toItems(messages)` でどちらを描くかを切り替えている。この構造から
次の症状が出ている。

- 送信した瞬間に `live` へ切り替わるため、そのセッションの過去のやり取りが画面から消える。
- ターンが終わると全件を取り直して `messages` へ戻すため、スクロール位置が飛ぶ。
- 同じ発言でも、生成中は `{kind, text, agent}`、確定後は `{role, content, agent_id}` という
  別の形で組み立てられる。`web/src/lib/Message.svelte` が両方を受け取るために分岐を持ち、
  片方の経路にだけ現れる表示の差異が生まれている。

**状態を表す語彙が足りない。** `web/src/app.css` が持つ面の色は `--bg` `--panel` `--panel-2`
`--line` の 4 つで、対話状態の表現は `button:hover { border-color: var(--accent) }` の 1 手しかない。
その結果、次が区別できない。

- マウスが乗っている / キーボードフォーカスがある / 選択されている
- 押している最中かどうか
- 操作できない状態かどうか

`web/src/` に `:focus-visible` も `outline` の指定も 1 つも無く、キーボードで操作したときに
現在位置が分からない。左パネルの選択行は `border-color: var(--accent)` で示しているが、
これは hover と同じ手段なので、マウスを乗せると選択行と見分けが付かなくなる。

**読むための作りになっていない。** 応答本文は `Message.svelte` が `white-space: pre-wrap` で
そのまま出しており、コードブロックも見出しも箇条書きも記法のまま並ぶ。設定は `App.svelte` の
`showSettings` が会話全体を差し替えるため、接続先を直している間は会話が見えない。自動スクロールは
`Chat.svelte` の副作用が更新のたびに `scrollTop = scrollHeight` を代入するので、遡って読んでいても
末尾へ引き戻される。セッションの削除は確認なしで実行される。

## ゴール / 非ゴール

### ゴール

- 表示モデルを 1 本にする。確定した履歴もストリーム中の内容も同じ構造で保持し、同じ経路で描く。
- 対話状態 (通常 / hover / 押下 / 選択 / キーボードフォーカス / 無効) を、それぞれ別の手段で
  区別できる配色の語彙を持つ。
- 応答本文を markdown として描画する。
- 情報密度の高いレイアウトにする。使用中のエージェントとモデル、ツールの実行、委譲の構造が
  常に画面上で追える。
- 設定を開いても会話が保たれる。
- 主要な操作をキーボードだけで行える。取り消せない操作には確認を挟む。

### 非ゴール

- **バックエンドの作り直し。** `/api` の形は変えない。ただしイベントに識別子を足す程度の
  追加は認める (詳細設計の「承認の対応付け」を参照)。
- **シンタックスハイライト。** 軽量なものでも 100KB 規模になり、単一バイナリへ埋め込む前提と
  釣り合わない。コードブロックは等幅と枠だけで示す。
- **CSS フレームワークとコンポーネントライブラリの導入。** 理由は代替案に書く。
- **ライトテーマ。** 暗い配色に固定する。ただし配色をトークンとして定義するので、後から
  段の定義を差し替えれば足せる状態にはしておく。
- **モバイル向けレイアウト。** 想定は手元の画面で常時開いておく使い方である。
- **仮想スクロール。** 想定する履歴の長さでは不要で、高さが可変な本文とは相性が悪い。
- **国際化。** 表示は日本語のままとする。

## 設計案

### 採用案

3 つの層に分けて作り直す。順に依存しているので、この順で着手する。

**1. 配色と状態の語彙を定義する。** 面と文字の色を、用途が固定された段階の並びとして持ち、
各段に次の役割を割り当てる。

| 段 | 役割 |
|---|---|
| 1 | 沈めた面 (コードブロック、設定の入力欄) |
| 2 | 左パネルの地 |
| 3 | 会話の地 |
| 4 | 持ち上げた面。操作できる要素の通常状態、および行に hover したときの面 |
| 5 | 押下中、および選択されている行の面 |
| 6 | 区切り線、操作できない要素の境界 |
| 7 | 操作できる要素の境界 |
| 8 | hover したときの境界 |
| 9 | 記号、無効な要素の文字 |
| 10 | 一覧の行の通常の文字 |
| 11 | 補助的な文字 |
| 12 | 本文の文字、一覧の行に hover したときの文字 |
| 13 | 見出し、選択されている行の文字 |

**面の並びは「地がいちばん暗い」ではない。** 会話の地 (段 3) を左パネル (段 2) より明るく
置き、入力欄の器 (段 4) をさらに明るく置く。どこが主役の領域で、いまどこへ書くのかを、
色の違いではなく面の順序そのもので示すためである。設定画面の入力欄だけは沈めた面 (段 1) を
使う。書き込む場所ではなく、値を収めてある場所だからである。

文字を 10・12・13 の 3 段に分けているのは、一覧の行の 通常 / hover / 選択 を、面の色だけで
なく文字の明るさでも表すためである。手段が 2 つあるので、選択を示すのに左端の帯を足す必要が
なくなる。

この並びを採る理由は、hover と選択とフォーカスが**別々の段**を使うようになり、同じ手段を
奪い合わなくなることにある。現状の不自然さは、hover も選択もアクセント色の境界線 1 つで
表していることに起因している。

アクセントは 1 系統に絞る。塗り (送信、保存、許可する) は**明るい青白の面に暗い文字**を
置く形とし、線 (縦線、リンク、フォーカスリング、生成中) はその面より濃い青を使う。塗りを
青いボタンにしないのは、画面の中でいちばん明るいものが「いま決めるべきこと」になるように
するためである。加えて、失敗を示す色を 1 系統だけ別に持つ。

**話し手の色。** エージェント ID から決まる 8 色を別に持つ。複数のエージェントが交代で話す
記録では、誰の発言かを追える手段が名前の文字列だけでは足りない。色相環を機械的に割ると
濁った色や浮いた色が混ざるため、会話の地に対して明度をそろえた 8 色を選んで持つ。利用者は
色を持たず段 13 で描く。人は常駐の話し手ではないためである。

トークンの命名は、面と、その上に乗る文字を対で持つ形にする。面の色を変えたときに文字色の
指定漏れが起きないようにするためである。名前の形は
`--surface` と `--surface-fg`、`--accent` と `--accent-fg` のように揃える。境界・リング・
補助文字は面から独立して `--border` `--ring` `--fg-muted` として持つ。

**2. 表示モデルを 1 本にする。** 画面はセッションごとに「発言の配列」を 1 つだけ持つ。
サーバーから読んだ確定履歴も、ストリームで届くイベントも、この配列に対する操作として表現する。

**3. レイアウトを組み直す。** 情報密度を優先する。左パネルは 240px 固定で、セッション名の
下にエージェント ID を補助色で添え、更新の新しさで区分にまとめる。右側の上端には、いま
使っているエージェントとモデル、中断ボタン、設定を出す。ツールの実行と委譲は本文と同じ
流れの中に 1 行ずつ置く。

**続けて同じ話し手が話す間は、名前と時刻を出し直さない。** ツールの行と委譲のまとまりは
話し手を切り替えない。それはそのエージェント自身の作業だからである。結果として 1 ターンが
1 つのまとまりになり、途中の作業がその中に収まる。

### 検討した代替案

- **CSS フレームワークを入れる。** トークンとユーティリティが最初から揃い、段階的な色の
  並びも用意されている。却下したのは、クラス列がテンプレートへ散り、ある要素の見た目を
  1 箇所で追えなくなるためである。この規模では素の CSS カスタムプロパティで足りる。

- **コンポーネントライブラリを入れる。** 状態表現もアクセシビリティも最初から整う。却下した
  のは依存の大きさで、単一バイナリへ埋め込む前提と釣り合わない。仕組みは持ち込まず、
  トークンの命名規約 (上記) だけを自前で定める。

- **見た目だけを差し替える。** 最も早い。却下したのは、生成中に履歴が消える、スクロールが
  飛ぶ、といった症状が描画経路の二重化に由来しており、CSS では消えないためである。

- **markdown を自前で最小実装する。** 依存を増やさずに済む。却下したのは、表・リンク・
  入れ子リストの取りこぼしが避けられないこと、そして無害化を自前で持つのが危ういことによる。
  モデルの出力をそのまま HTML として挿入する以上、無害化は実証された実装に任せる。

- **仮想スクロールを入れる。** 長い履歴で有利になる。却下したのは、高さが可変で、しかも
  ストリーム中に伸び続ける本文とは噛み合わないことによる。必要になってから考える。

### 追加する依存

実行時の依存として次の 2 つを入れる。合計で 30KB 前後 (gzip 後) の増加を見込む。

- **marked** — markdown を HTML へ変換する。
- **DOMPurify** — 変換された HTML を挿入前に無害化する。

加えて、欧文の書体として **@fontsource/inter** と **@fontsource/jetbrains-mono** を入れる。
使うのは latin 部分集合の woff2 だけで、合計 115KB 前後。同梱される woff は指さない。これを
読む環境はすべて woff2 を扱えるので、同じ字形を 2 度持つことになるためである。

加えて、表示モデルの単体テストのために **vitest** を開発時の依存として入れる。配布物には
含まれない。

## 詳細設計

### 状態の表し方

操作できる要素はすべて、次の規則で状態を表す。要素ごとに違う表現を作らない。

- **通常** — 面は段 4 (一覧の行のように地に溶かす要素は透明)、境界は段 6、文字は段 10。
- **hover** — 面を段 5 へ、境界を段 8 へ、文字を段 12 へ動かす。境界だけを変える現在の
  やり方は取らない。面が動かないと、押せる範囲がどこまでかが伝わらない。
- **押下中** — 面をもう 1 段。位置や大きさは動かさない。
- **選択** — 面を段 5 にしたうえで、文字を段 13 へ上げる。左端に帯は置かない。文字の
  明るさが 2 つ目の手段になるので、hover と重なっても区別が付く。
- **キーボードフォーカス** — アクセントの線の色で 2px のリングを 2px 外側に出す。
  `:focus-visible` に限り、マウスで押したときには出さない。リングは hover とも選択とも
  別の手段なので、3 つが同時に成立しても読み取れる。
- **無効** — 前景を段 9 へ落とし、境界を段 6 に戻す。不透明度を下げる方法は取らない。
  文字が背景に溶けて読めなくなるためである。

ツールの行は、実行の結末も同じ考え方で描き分ける。成功・失敗・拒否に加えて、**中断で止まった**
状態を別に持つ。止めたのは利用者なので、失敗として赤く示すと原因を取り違える。

結末は記号 (`✓` `✕`) ではなく、6px の角丸の四角の色と塗りで示す。**塗りは走らせた結果、
中抜きは走らずに終わったこと**を表す。

| 結末 | 見せ方 |
|---|---|
| 実行中 | アクセントの線の色の塗り |
| 成功 | 成功の色 (緑) の塗り |
| 失敗 | 失敗の色 (赤) の塗り |
| 拒否・中断 | 段 7 の中抜き |
| 承認待ち | アクセントの線の色の中抜きと「承認待ち」の語 |

成功にも色を割く。失敗だけが色を持つと、灰色の四角が「まだ何も起きていない」と「終わった」
の両方を指すことになり、終わったかどうかがその場で読み取れない。実行中から成功へは色が移る
ので、移り変わり自体が完了の合図になる。

一覧の行は、hover / フォーカス / 選択 (パネルが活性のとき) / 選択 (非活性のとき) の 4 つを
区別する。左パネルからフォーカスが外れているときの選択行は、面を段 4 相当まで弱める。
いまどちらのペインを操作しているかが分かるようにするため。

**変化のさせ方。** 遷移させるのは `background-color`、`border-color`、`color` のみで、
時間は 150ms、曲線は ease-out とする。150ms より速いと変化が知覚されず、遅いと反応が鈍く
感じられる。位置と大きさは動かさない。動く要素が多いほど、どこを見ればよいか分からなくなる。

例外は 1 つだけ、**生成中を示す 3 点の明滅**とする。その場から動かない小さな指標であり、
画面の配置を動かさないためである。`prefers-reduced-motion` が指定されている環境では遷移
時間を 0 にし、明滅も止めて静止した 3 点にする。

### 文字組み

大きさは 3 段階に留める。見出し (セッション名、設定の節)、本文、補助 (エージェント ID、時刻、
ツールの所要時間)。太さは 2 段階。等幅フォントは識別子 — モデル名、ツール名、パス、コード —
にだけ使い、地の文には使わない。時刻と所要時間は等幅の数字で桁をそろえる。並んだときに目が
数字の位置で迷わないようにするためである。

**欧文の書体は同梱する。** 地の文には Inter (400/500/600)、識別子には JetBrains Mono
(400/500) の latin 部分集合を woff2 で持つ。単体バイナリとして配るため配信元から取り寄せる
方法は使えず、OS の既定に任せると環境ごとに字面が変わる。選ぶ基準は 13px という寸法で崩れ
ないことに置く。x ハイトが低く線の細い書体は、この大きさでは字面が痩せて縁が荒れる。

和文は同梱しない。字形を持たない指定は次の候補へ落ちるので、`Yu Gothic UI` などの OS の
書体がそのまま使われる。和文まで含めると数 MB になり、単体バイナリという前提と釣り合わない。

**`-webkit-font-smoothing: antialiased` は指定しない。** macOS では細く整うが、Windows では
副画素による描画を切ってしまい、暗い地の上の明るい文字が痩せて縁が荒れる。既定の描画に任せる。

markdown の見出しは、大きさと明るさの両方で本文と段を付ける。1px の差では読み分けられない。

### 画面構成

左パネルは幅 240px で固定し、上から順に、プロダクト名と提供元の接続状態、セッション一覧、
操作 (新しい会話 / 再読込 / 設定) を置く。一覧の各行はセッション名と、その下にエージェント ID を
補助色で持つ。本文に集中したいときのために、左パネルは畳める。

一覧は更新の新しさで **今日 / 昨日 / 過去 7 日 / それ以前** の区分にまとめる。区分は暦日で
数える。24 時間で数えると「昨日の 23:59」と「今日の 00:01」が同じ区分に入り、日付を手掛かりに
探せなくなる。話し手の色は一覧では使わない。8 色が並ぶと、どれが選択されている行かという
本来の区別を邪魔するためである。

**面の順序。** 左パネル (段 2) < 会話の地 (段 3) < 入力欄の器 (段 4) とする。

右側は上端に、セッション名、エージェントの選択、使用中のモデル名、生成中なら中断を置く。
モデル名を常時出すのは、複数のモデルを行き来する使い方で「いまどれで答えているか」が
最も知りたい情報だからである。

**設定は会話を差し替えない。** 画面の中央に浮かせる窓として重ねて開き、閉じると元の会話が
そのまま残る。接続先を直してすぐ会話へ戻る、という往復が主な使い方になるためである。

右端へ寄せない。右端は今後の右パネルの置き場として空けておく。高さも画面いっぱいにはせず、
上下に地を残す。地が見えていないと、脇へ寄せた板に見えて、閉じれば元へ戻るものだと伝わらない。

### 表示モデル

セッションごとに発言の配列を 1 つ持つ。この配列に対する操作は 3 つだけとする。

- **追加** — 新しい発言を末尾に置く。
- **追記** — 識別子で指した発言の本文に文字を足す。
- **確定** — 識別子で指した発言に、完了または失敗という結末を付ける。

確定履歴の読み込みは「配列全体を追加で組み立てる」操作として表し、ストリームのイベントは
上の 3 操作へ写す。`message_start` は追加、`delta` は追記、`message_end` と `error` は確定、
`tool_call` と `tool_result` と `delegate_start` と `delegate_end` は追加にあたる。生成が
終わったときに全件を取り直さない。取り直すのは、セッションを開いたときと、再読込を押したときに限る。

委譲の入れ子は、サーバーが持っている親子関係をそのまま使う。ストリーム中も同じ形を作る。

満たすべき制約:

- 生成中も、そのセッションの過去の発言が画面から消えない。
- 生成が途中で失敗しても、そこまでの本文が残り、失敗した事実がその発言に付く。
- 同じ発言が二重に現れない。識別子が同じものは同じ発言として扱う。
- 表示のためだけの状態 (畳んでいるかどうか、など) を発言の配列に混ぜない。

### ツール実行と委譲の見せ方

ツールの呼び出しは、本文と同じ幅の 1 行として流れの中に置く。行にはツール名、主要な引数、
所要時間、成否を出す。既定は畳んだ状態で、開くと引数の全体と結果が見える。

委譲は子の発言をひとまとまりにし、左に縦線を引いて階層を示す。**縦線は渡した先の話し手の色で
引き**、上端と下端を折り返して、呼び出した行と返ってきた成果に結び付ける。線の色そのものが
「誰に渡したか」を伝えるので、名前を読み直さなくても階層をたどれる。基盤設計が「子の途中経過は
履歴に保存し、UI では追える」と定めているのは、この形を指す。

委譲は**既定で開く**。渡した先の仕事は経過ではなく中身であり、畳んだままだと何が起きたのかが
読めない。畳めば「どのエージェントに何を頼み、何が返ったか」が 1 行で読める。

**縦線は 1 つの階層につき 1 本に留める。** ターン全体を括る話し手の線は最上位でだけ引く。
委譲の中では囲んでいる線が既に話し手を示しているので、そこで括ると同じことを言う線が 2 本
並ぶ。

受け取った成果は、多くの場合そのまま子の最後の発言である。同じ文章が続けて 2 度並ばないよう、
成果が子の最後の発言と違うときにだけ本文を出す。同じときは、そこで終わったことだけを示す。

**承認の対応付け。** 承認を求める表示は、対応するツール呼び出しの行の直下に出す。画面の下端に
固定しない。何に対する承認かが離れると判断できないためである。

対応付けにはツール呼び出しの識別子を使う。識別子は `tool_call`、`tool_result`、
`approval_request`、`delegate_start`、`delegate_end` のすべてが持つ。委譲は 1 つのツール呼び出しから
始まるので、その開始と終了も同じ識別子で親の行に結び付く。識別子は 1 ターンを通して一意で
なければならない。提供元が返す呼び出し ID は 1 回の生成の中でしか一意でなく、ツールの反復で
同じ値が再び現れるため、要求した発言の識別子と呼び出しの位置から組み立てる。

### markdown の描画

描画の対象は、エージェントの応答本文とツールの結果に限る。利用者の入力はそのまま表示する。
記法のつもりで書いていない文字列が解釈されると、書いたものと表示が食い違うためである。

変換して無害化してから挿入する。順序を逆にしない。コードブロックは等幅で、横に溢れる場合は
その中だけを横スクロールさせ、言語名とコピーの手段を添える。

生成中は、閉じていないコードフェンスのような不完全な markdown が届く。トークンごとに解析を
やり直さず、100ms の間隔で描画を更新する。

### スクロール

末尾へ追従するのは、利用者が既に末尾付近にいるときだけとする。遡って読んでいる間は位置を
動かさず、新しい内容が届いたことは「最新へ」の案内で示す。

判定は、末尾に置いた目印がスクロール範囲に入っているかどうかと、内容の高さの変化の監視で行う。
更新のたびに `scrollTop` へ代入する現在の方法は取らない。利用者の操作と区別が付かないためである。

### 始める操作と止める操作

**同じ場所に置く。** 走らせるのも止めるのも入力欄の同じボタンで行い、画面上端には中断を
置かない。走っているものを止めるのだから、探す場所も同じであるべきである。ボタンは語では
なく形で示す。待機中は再生の三角、生成中は停止の四角とする。

止めるボタンには、進行中を表す色 (ツールの行の実行中の印と同じ色) をそのまま使う。止める
対象が何であるかを、新しい色を増やさずに伝えるためである。

### キーボードと取り消せない操作

- 送信は Enter、改行は Shift + Enter、生成の中断は Esc。Ctrl + Enter も送信として受ける。
  以前の打ち方を覚えている指がそのまま動くようにするためである。
- **変換中の Enter では送信しない。** 和文を打っているときの Enter は候補の確定であり、
  これを送信とみなすと確定した瞬間に書きかけが飛ぶ。変換中の Esc も同様に、候補の取り消しで
  あって生成の中断ではない。
- **生成中は書けるが送れない。** 返ってくるのを待つ間に次の依頼をまとめられるようにする。
  送れないことは入力欄の案内で伝え、書きかけは消さない。
- 記録の中には開閉できる行が多く並ぶ。Tab だけで入力欄へ届こうとするとその全部を通り抜ける
  ことになるので、文字を打ち始めたら入力欄へ焦点を移す。重ねて開いている画面があるときは
  移さない。
- 入力欄は打った分だけ伸ばし、上限に達したらその中でスクロールさせる。行数を決め打つと、
  短い依頼では無駄に空き、長い依頼では書いたものが見えない。
- セッション一覧は上下キーで移動し、Enter で開く。
- セッションの削除は確認を挟む。取り消せない操作を 1 クリックで実行させない。
- 操作できる要素はすべて Tab で到達でき、到達したことがフォーカスリングで分かる。

### 失敗の見せ方

サーバーは失敗の種類を返している。接続できない / モデルが無い / モデルがツールに対応していない /
対象が無い、の 4 つである。これを種類ごとに、起きたことと次に取るべき行動の 2 つの文で出し分ける。
種類を無視して同じ文言にすると、利用者は提供元の起動忘れなのか設定の誤りなのかを判断できない。

提供元へ接続できていないことは、左パネル上端の状態表示でも常時分かるようにする。

**同じ失敗を 2 か所に出さない。** 失敗の種類はストリーム上のイベントにも載せ、上端の帯が
既に伝えている内容と重なる通知は出さない。また、実行ループが失敗をイベントとして流したあと、
同じ error を受け取った側がもう一度流さないようにする。同じ文が 2 度並ぶと、どちらを読めば
よいか分からなくなる。種類の判定は 1 か所に置く。ストリーム上の失敗と HTTP の失敗で分類が
食い違うと、同じ原因が画面上で別物として見えるためである。

画面だけが持つ項目 (送信直後の本文、通知) の識別子に時刻を使わない。同じミリ秒に 2 件届いた
ときに同じ値になり、描画が同一の項目と誤認する。

## テスト方針

自動で検証できるのは表示モデルだけなので、そこに絞って単体テストを置く。イベントの列を与えて
配列の状態を検証する形にする。少なくとも次を確認する。

- 履歴の読み込みと、その後のストリームが同じ配列に対して破綻なく積まれること。
- 途中で失敗したとき、そこまでの本文が残り、その発言に失敗が付くこと。
- 同じ識別子の発言が二重に入らないこと。
- 委譲の子が親の下にまとまること。
- 同じ瞬間に届いた通知が同じ識別子にならないこと。

表示の規則のうち、状態を持たずに決まるものは純関数として切り出し、そこにも単体テストを置く。

- 話し手の色 — 同じ ID からは常に同じ色が出ること。並べ替えただけの ID が同じ色にならない
  こと。8 つの枠が埋まること。
- 名前を出す位置 — 同じ話し手の連続が 1 つの名前行になること。ツールの行と委譲のまとまりが
  話し手を切り替えないこと。
- 送信の判定 — Enter は送信し、Shift + Enter と**変換中の Enter は送信しないこと**。
- 一覧の区分 — 暦日で数えること。

markdown の無害化は、`script` 要素や `javascript:` を含む入力を与えて、挿入される内容から
取り除かれることを確認する。

残りは手で確認する。実装が終わった時点で次を通す。

- 生成中に、そのセッションの過去の発言が画面に残り続けること。
- 遡って読んでいる間にスクロールが引き戻されないこと。末尾にいるときは追従すること。
- 設定を開いて閉じたあと、会話がそのまま残っていること。
- Tab だけで会話の開始・送信・中断・設定変更ができること。
- Tab で移動したときはフォーカスリングが見え、マウスで押したときは出ないこと。
- 一覧の行で、hover と選択とフォーカスが同時に成立しても 3 つを読み取れること。
- 提供元を止めた状態で送信したとき、次に取るべき行動が画面から読み取れること。送った本文が
  消えないこと。同じ内容が 2 か所に出ないこと。
- 委譲の縦線が渡した先の色で引かれ、上端と下端が折り返して閉じていること。
- 面の順序 (左パネル < 会話の地 < 入力欄の器) が実際にそう見えること。
- 和文を入力して変換の Enter で送信されないこと。
- 幅を狭めても横に溢れず、入力欄が画面の外へ出ないこと。

## リスクと未決事項

- **左パネルを畳んだ状態を覚えるか。** いまは覚えず、起動のたびに開いた状態から始まる。
  覚えるならブラウザ側に保存することになる。会話の内容ではないので保存して差し支えないが、
  必要になるまで持たない。
- **委譲が深いときの表示。** 縦線を渡した先の色で引くようにしたので、2 段までは色で追える。
  上限の 3 段では窮屈になる可能性が残る。深い委譲を実際に走らせて判断する。
- **話し手が 9 体以上いるとき。** 色は 8 つしか持たないので、9 体目からは既に使われている色と
  重なる。同時に画面へ出る話し手の数を考えると当面は足りるが、重なったときに何で見分けるかは
  決めていない。
- **長い履歴での描画の重さ。** 発言の数だけ要素が積まれる。想定する長さでは問題ないと
  見込んでいるが、重くなるようなら描く範囲を絞る。仮想スクロールは最後の手段とする。
