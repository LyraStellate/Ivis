## 背景と課題

Ivis はブラウザの前にいるときしか使えない。待ち受けを開けて Tailscale 越しに繋げるようにはしたが (#694381)、結局どこかで Ivis の画面を開く必要がある。手が離せないときや外出先で「これ調べておいて」と投げる相手にはなっていない。

ボットは既に用意してある。Discord から呼べれば、入口が 1 つ増えるだけでなく、既に人が居る場所へ Ivis が入っていくことになる。

技術的には、この機能に必要な部品はほぼ揃っている。`engine.Engine.Run` は「セッション ID・本文・イベントの受け口」だけを受け取り、HTTP には依存していない (`internal/engine/run.go`)。ツール実行、委譲、承認、作業ディレクトリの分離 (#903215) はすべてセッション単位で動く。足りないのは次の 3 つである。

1. **Discord と会話の対応付け。** `sessions` にはどこから来た会話かという情報が無く、Discord のチャンネルから対応する会話を引く手段がない。
2. **実行の占有と承認の窓口が HTTP 層に固定されている。** 同じセッションで 2 つのターンが同時に走らないための占有 (`internal/httpapi/stream.go` の `running`) と、承認の待ち合わせ (`pending`) は `httpapi.Server` が持っている。Discord から始まった実行はこのどちらも使えない。承認を求めても、応える手段が画面にしかない。
3. **Discord 向けの描画。** イベントの列を、チャンネルに並ぶメッセージの列へ落とす部分。

## ゴール / 非ゴール

### ゴール

- 設定画面でトークンを入れて有効にすると、Ivis を再起動せずに Discord へ接続する。
- ボットがメンションされたときだけ、そのメッセージへのリプライとして応答する。
- 生成中の様子が Discord 上で見える。ツール実行と委譲が起きた順に残り、推論は伸びていく。
- 呼びかけの先頭に `/` を付けると、エージェントではなく Ivis 自身への指示になる。走っている実行を止める、履歴を消す。
- 読み込み中・生成中は「〜が入力中」を出す。
- 承認の要るツールを呼んだとき、Discord 上のボタンで応えられる。
- チャンネルごとの会話が Web の一覧から読め、巻き戻しと担当エージェントの変更ができる。

### 非ゴール

- **Discord のスラッシュコマンドとしての登録。** コマンドは呼びかけの本文で見分ける。理由は詳細設計に書く。
- **引数を取るコマンド。** いまのところどれも対象が「このチャンネルの会話」1 つに決まる。名前の後ろは読むが、使ってはいない。
- **権限による制限。** 誰が打っても同じように効く。招待した場所にしか居ないので、招待の管理がその役割を果たす。
- **DM での応答。** DM ではメンションが成立しないため、「メンションされたときだけ」という線引きがそのままでは使えない。別の線引きが要るので今回は外す。
- **Web からの Discord セッションへの送信。** 読む・巻き戻す・担当を変えるまで。理由は詳細設計に書く。
- **反応するサーバーやチャンネルの制限。** ボットを招待した場所にしか居ないので、招待の管理がその役割を果たす。
- **添付ファイル・画像・音声。** 受け取るのも返すのも本文だけ。
- **ボットが不在だった間の会話の取り込み。** メンションされた 1 通だけを入力とする。
- **Discord 側のメッセージの巻き戻し。** 会話は戻せるが、投稿済みのメッセージは消さない。ワークスペースを戻さないのと同じ理由 (#903215)。
- **複数ボット・複数トークン。**

## 設計案

### 採用案

**`internal/discord` に、Discord Gateway と `engine.Engine` を繋ぐブリッジを置く。** ブリッジは Ivis の一部として常駐し、メンションを受けたら対応するセッションで 1 ターン走らせ、その経過をチャンネルへ時間順に並べていく。

全体は次の 3 つに分かれる。

- **接続** — Gateway への接続・切断と、メンションの受け口。設定の保存で再接続する。
- **描画** — エンジンのイベント列から「いま Discord に並んでいるべきメッセージの列」を組み立てる。ここは外部と一切やり取りしない純粋な部分にする。この機能で一番作り込むのがここで、試験もここに集まる。
- **送信** — その列と、実際にチャンネルにあるものとの差を埋める。足りないものを投稿し、変わったものを書き換え、要らなくなったものを消す。一定の間隔でだけ行う。

イベントの受け口と送信を分けるのが、この設計の要である。`engine.Run` の `emit` は生成ループから同期的に呼ばれるので、そこで Discord へ HTTP を投げると、送信の待ち時間だけ生成が止まる。`emit` は手元の状態を更新するだけにして、送信は別に走らせる。

**接続には `github.com/bwmarrin/discordgo` を使う。** 純 Go で cgo を要求しないため、単一バイナリの前提 (#694381) は保たれる。Gateway のハンドシェイク・ハートビート・再接続と REST のレート制限は、いずれも自分で書けば相応の量になり、しかも Discord 側の仕様変更に追従し続けることになる。

**Discord のチャンネル 1 つが Ivis の会話 1 つに対応する。** 場所が変われば話も変わるので、文脈もそこで切れているのが自然である。同時に別のチャンネルで呼ばれたときにも、互いを待たずに走れる。

### 検討した代替案

**Discord 全体を 1 つの会話にまとめる。** 一覧に固定で 1 行置けばよく、対応表も要らない。ただし別々のチャンネルの話が同じ文脈に混ざり、同時に 2 人が呼ぶと片方が待たされる。ボットが複数のチャンネルに居る運用では成り立たない。

**スレッドごとに 1 つにする。** 話題ごとに文脈が綺麗に切れるが、スレッドを使わない運用ではチャンネルごとと同じ結果になり、使う運用では会話が際限なく増える。チャンネル単位なら、必要なときに Web 側で巻き戻せば文脈は切れる。

**WebSocket ライブラリだけを入れて Gateway を自前で話す。** 依存は薄くなるが、書く量とその後の保守が大きく増える。Ivis 本体の価値はそこには無い。

**承認を Web 画面だけで受ける。** 実装は増えないが、Discord から呼んだのに承認は画面を開かないと返せない、という状態になる。外出先から投げられることがこの機能の主眼なので成り立たない。

**経過を 1 通の埋め込みにまとめ、完了時に要約へ縮める。** 最初はこの形で作った。Web 画面の「終わったら畳む」に対応させたつもりだったが、実際には 2 つの問題がある。まとめた枠は回答の直前か直後に置くしかなく、前に置けば経過が回答に押し流されて消え、後ろに置けば回答を読んだ後に要らない数字が並ぶ。そして縮めた時点で、何をどの順にやったかが失われる。時間順に並べる形へ変えた。

**委譲の中身をスポイラー (`||...||`) に隠す。** Web の折りたたみに一番近い見た目になるが、Discord のスポイラーは押すと二度と閉じられず、長い経過を隠すと押した後の見通しがかえって悪い。

**メンションで止める (「@bot 止まれ」)。** コマンドを登録せずに済むが、打った内容が新しい依頼と見分けられない。止めるつもりの一言が次のターンを始めては元も子もない。

## 詳細設計

### 前提となる Discord 側の制約

設計の形はこれらから決まるので、先に挙げておく。いずれも Ivis 側では動かせない。

- メッセージ本文を読むには、Developer Portal で **Message Content Intent** を有効にする必要がある。有効にしないとメンションは届いても本文が空で来る。
- メッセージ本文は **2000 文字**、埋め込みの説明文は 4096 文字まで。
- 「入力中」は投稿するたび **約 10 秒**で消える。続けるには送り直す。
- 同じチャンネルへの編集にはレート制限があり、超えると 429 と待ち時間が返る。

### データモデル

`sessions` に 2 つ足す。

- **出自** — その会話がどこから始まったか。`web` と `discord` の 2 値で、既存の行は `web` として扱う。
- **チャンネル ID** — Discord から来た会話が対応するチャンネル。Web の会話では空。

チャンネルと会話は 1 対 1 に保つ。空でないチャンネル ID に対して一意になる索引を張り、二重に作られないようにする。既存のデータベースへは、列の追加も索引の作成も後から加えられるので、いまある移行の仕組み (`internal/store/store.go` の `migrations`) にそのまま並べる。

引き当ては「チャンネル ID から会話を 1 件返す」操作を足す。無ければブリッジが新しく作る。このとき、

- 担当エージェントは設定の既定エージェント。以後は Web 側でいつでも変えられる。
- 表題はチャンネル名にする。最初の依頼で表題を付ける既存の処理 (`maybeSetTitle`) は「新しい会話」のときだけ働くので、名前を入れておけば上書きされない。チャンネルごとに 1 本である以上、名前は話題ではなく場所であるべきなので、これでよい。
- 作業ディレクトリは会話を作った時点で用意する。Web の会話と同じ扱い (#903215)。

**発言者は本文の先頭へ付ける。** チャンネルには複数の人が居るので、誰の発言かが分からないと会話が成り立たない。保存する本文自体を `表示名: 本文` の形にし、モデルへも履歴表示へも同じものが渡る。

代替案として `messages` に発言者の列を足すことも考えたが、モデルへ渡す段では結局本文へ混ぜることになり、列を増やしても表示以外に使い道がない。列が増えれば、巻き戻しも委譲も履歴の読み出しも、そこを通る経路すべてが影響を受ける。

### 設定

設定に Discord の項目を足す。有効かどうか、トークン、の 2 つだけを持つ。

編集の間隔は設定に出さない。適切な値は環境ではなく Discord のレート制限で決まるうえ、実際に 429 が返ればそこから間隔を伸ばせばよい。設定で持たせると、利用者が詰めすぎた値を入れられる余地だけが残る。

トークンの扱いは既存の検索 API 鍵 (`search_api_key`) に揃える。値を送らなければ変更しない形にして、画面から消すこともできるようにする。設定ファイルには平文で載る。

設定を保存したら、接続先を作り直す既存の処理 (`refreshProvider` / `refreshSearch`) と同じ場所で、Discord の接続も張り直す。有効から無効になれば切断し、トークンが変われば繋ぎ直す。再起動を要求しない。

起動状態 (`/api/status`) に Discord の接続状態を足す。繋がっているか、失敗しているならその理由。ここに出さないと、トークンを間違えたことに利用者が気付けない。

### 実行の占有と承認の窓口

いま HTTP 層が持っている「そのセッションで生成が走っているか」の占有を、Web と Discord の両方から見える場所へ移す。移さないと、Web で送信中のセッションへ Discord からメンションが来たとき (逆も同じく) に、同じ会話で 2 つのターンが同時に走り、履歴の書き込み先が衝突する。

**承認の窓口は、その実行がどこから始まったかで決まる。** Discord から始まった実行はボタンで受け、Web から始まった実行は今まで通り画面で受ける。判定に使えるのは承認要求に載っているセッション ID で、それを Discord ブリッジがいま動かしているかどうかが答えになる。既存の窓口が最初に受け、ブリッジの管轄ならそちらへ渡す。エンジンから見える受け口は 1 つのままなので、エンジン側の構造は変えずに済む。

ブリッジが「自分の管轄」と答えるのは、実際にそのターンを走らせている間だけにする。会話の出自 (Discord から始まった会話かどうか) で判定すると、連携を切った後や、そのターンを誰も見ていないときにも、返らない要求を待ち続けることになる。

### Discord 上の描画

**経過も回答も 1 通のメッセージに収め、書き換えながら伸ばす。** 枠 (埋め込み) は使わない。分かれるのは、上限を超えて 1 通に収まらないときだけである。出来事ごとにメッセージを分ける形も試したが、1 回のやり取りがチャンネルを何通も占め、他の人の会話の中でひとまとまりに見えなくなる。

**何が回答で何がそうでないかは書式で分ける。回答だけが飾りの無い地の文になり、それ以外はすべて何らかの形で囲われている。** 絵文字は使わない。記号が増えるほど 1 行の情報が濃くなり、かえって流し読みできなくなる。

- **推論** — コードブロック。省略せずに伸ばし、終わったら「推論: n 秒」だけを入れたコードブロックへ縮める。途中を切り詰めると、何を考えていたかを追う手段が無くなるので、長さでは切らず、終わった時点で畳む。区切りと同じ記号が推論の中に混ざるとそこで切れるので、取り除いてから囲う。
- **ツール** — 名前と段階を 1 つのインラインコードにまとめる (`` `run_command : running` ``)。段階は running / approval / complete / failed / aborted の 5 つで、名前と揃うので語も英語にする。結果を待たずにターンが終わったものを complete と書かないのは、止めたのに終わったように見えては、何が起きたかを取り違えるためである。引数と失敗の理由だけは次の行へ小さく出す。承認は何を通すのかが無ければ選べず、失敗は理由が無ければ次の手が決まらない。
- **委譲** — 引用として一段内へ寄せ、任された先の出来事をその中に収める。中の見せ方は外と同じで、推論は伸びて縮み、ツールは段階を書き換える。走り終わったら「> **Researcher へ委譲**」の 1 行へ単純化する。名前は定義に付けた表示名を使う。入れ子の委譲はさらに一段内へは寄せず、それ自身の塊を持つ。
- **失敗** — 太字の見出しを付けて本文と区別し、種類が分かるなら次に取るべき行動を小さく添える。
- **回答** — 飾りを付けない。手前の経過との間を 1 行空けるので、囲われていないことと合わせて、経過の続きではないと目で分かる。

**回答の後ろには何も付けない。** 所要時間も、文脈をどれだけ使ったかも出さない。読みたいのは答えであって、その周辺の数字ではない。

### コマンド

**呼びかけの本文の先頭が `/` かどうかで見分ける。** メンションを受けたらまずコマンドかを判断し、そうであれば実行して返す。エージェントへは流さない。

Discord のスラッシュコマンドとして登録しない理由は 2 つある。登録には招待に `applications.commands` が要り、既に招待済みのボットでは入れ直しになる。サーバーごとの登録は反映が遅れることがあり、入れた直後に止められないのでは緊急停止の役に立たない。本文で見分ければ、決まりは 1 つで済む — 用があるときは必ずメンションし、先頭に `/` があればそれは Ivis への指示、無ければエージェントへの依頼である。

- 名前は英字だけとし、大文字小文字は問わない。打った本人にはどちらを打ったか見えているので、別のものとして扱うと効かない理由が分からない。
- 知らない名前には、使えるものの一覧を返す。黙ってエージェントへ流すと、コマンドのつもりで書いたものがそのまま依頼として実行される。
- 対象はそのコマンドを打ったチャンネルの会話とする。会話はチャンネルに 1 つなので、それ以上の指定は要らない。会話がまだ無ければ、その旨を返して何もしない。
- **使える相手を絞らない。** 承認は実行を通す操作なので呼びかけた本人に限るが、コマンドはそうではない。特に止めることは誰にとっても安全で、その場に居合わせた人が止められないなら緊急停止の役に立たない。

いま持つのは 3 つ。

- **`/stop`** — 走っているターンを打ち切る。推論がループしたときのように、こちらから止めるほかない状態は必ず起きる。中断の口が無ければ、上限 (`MaxIterations`) に当たるまで待つか、Ivis ごと落とすことになる。止めるとそこまでに出たものは残り、結果を待たずに終わったツールは aborted になる。走っていなければその旨を返す。「止めました」と返しては、何が起きたのか分からない。
- **`/clear`** — その会話の履歴をすべて消す。会話そのものは残す。消して作り直すとチャンネルとの結び付きが張り直され、そのときに作業ディレクトリも別の場所になる。話の続きを捨てたいだけの人が、置いたファイルまで失う。生成中は断る。走っている最中に消すと、そのターンが自分の書き込み先を失う。取り消せないので、消した件数を返す。数だけでも残らないと、打ち間違いに気づく手がかりが無い。
- **`/help`** — 使えるものの一覧。

押しボタンは置かない。ボタンを置くには走っていることを示す通が要るが、それは 1 通に収める形と噛み合わない。

走っていることを示す専用のメッセージは置かない。「入力中」がその役目を負う。ただし**何も出ないまま終わった場合は、その旨を 1 行返す**。黙って終わると、呼びかけが届いていないのか、届いて何も返らなかったのかが区別できない。

### 送信の間引き

出来事が起きるたびに送っていてはレート制限に当たる。送信側は、あるべき並びと実際にあるものとの差を、次のように埋める。

- 一定の間隔でだけ Discord へ反映する。既定は 1.5 秒に 1 回とし、実測で詰める。
- 前回送った内容と変わっていなければ送らない。
- 投稿は並びの順に行い、途中で失敗したらそこで止める。飛ばして次を出すと、出来事の順が入れ替わる。
- 消せなかった場合は投稿を続ける。権限が足りずに消せないだけで回答が出なくなるのは釣り合わない。次の回にまた試みる。
- 429 が返ったら、返された待ち時間だけ待ち、間隔を倍にする。上限は 8 秒。成功が続けば元へ戻す。
- ターンが終わったときは、間隔を待たずに最終形へ反映する。

本文が 2000 文字を超えるものは複数のメッセージへ分ける。切る位置は行の切れ目を選び、コードブロックの内側で切るときは閉じてから開き直す。閉じないまま切ると、続きのメッセージ全体がコードとして表示される。引用の中のコードブロックも同じに扱う。引用の印が前に付くだけで見落とすと、委譲の中の推論を切ったときに開いたままになる。

呼びかけへのリプライになるのは、最初に出た中身 (推論・ツール・回答のいずれか早いもの) である。

### 入力中インジケーター

メンションを受けた時点から出し始め、約 8 秒ごとに送り直す。ターンが終われば止める。承認待ちの間も止める。押されるまで動かないのはボットではなく人間の側なので、そこで「入力中」を出し続けるのは嘘になる。

### 承認ボタン

承認が要るツールに当たったら、ボタンを 2 つ (実行する / やめる) 付ける。停止と違って押しボタンにするのは、対象が「いまこの 1 回の呼び出し」だからである。コマンドにすると、どの呼び出しへの返事かを言い添えることになる。ボタンは最後の通に付ける。伸びていく先がそこなので、承認を求めた場所が画面の外へ出ない。何を承認するのかは同じ通の中に出す。引数は長くなりうるので、表示は適当な長さで切る。

- 押せるのは**呼びかけた本人だけ**。他の人が押した場合は、その人にだけ見える形で断る。
- 5 分で期限切れとし、拒否として扱う。エンジン側は拒否をモデルへ返して続行できるので (`internal/engine/exec.go`)、ターン全体が失敗するわけではない。
- 押されたか期限が切れたらボタンを消す。押せるように見えて何も起きないボタンを残さない。

### Web 画面

会話一覧の先頭に「Discord」という固定の区分を置き、その下にチャンネルごとの会話を並べる。日付による区分 (`byBucket`) より前に出す。連携していないときは区分ごと出さない。

**Discord の会話は Web からは送信できない。** 読む・巻き戻す・担当エージェントを変えるまでとする。Web から送っても、その内容は Discord のチャンネルには出ない。次にそのチャンネルで話す人は、自分の知らない文脈が挟まった状態で会話を続けることになる。同じ会話を 2 か所から進められることの分かりにくさに対して、得られるものが釣り合わない。入力欄には送れない理由を出す。

設定画面には Discord の欄を置く。有効の切り替え、トークン、接続状態、そして必要な権限と Message Content Intent の説明を出す。この 2 つは Ivis 側からは設定できず、知らないと必ず躓く。

### 処理フロー

メンションを受けてから応答が終わるまで。

1. Gateway からメッセージの作成が届く。
2. 自分へのメンションが無ければ何もしない。自分自身と他のボットの発言も無視する。互いにメンションし合う 2 体が居ると、止まらない往復になる。
3. チャンネルに対応する会話を引く。無ければ作る。
4. その会話で既に生成が走っていれば、その旨をリプライして終わる。待ち行列は作らない。
5. 「入力中」を出し始める。
6. 本文からメンションの表記を取り除き、発言者を前置してエンジンへ渡す。
7. 流れてくるイベントで手元の状態を更新し、送信側が一定間隔でメッセージへ反映する。
8. 終わったら最終形へ反映し、「入力中」を止める。

異常時。

- **提供元が落ちている、モデルが無い** — エンジンが種類付きで失敗を流す (`KindOf`)。太字の見出しを付けて出し、種類に応じた一言を添える。何も出さずに黙るのが一番悪い。
- **Discord への送信に失敗する** — 権限不足などが考えられる。ログへ出し、生成自体は続ける。履歴には残るので、Web 側からは読める。
- **接続が切れる** — 再接続はライブラリに任せる。切れている間に来たメンションは取りこぼしうる。取りこぼしを埋めるには不在中のメッセージを読み直すことになり、それは非ゴールにした。
- **トークンが無効** — 起動状態に理由を出す。設定画面から直せる。

## テスト方針

外部と繋がる部分と、繋がらない部分を分ける。作り込みの大半は後者にあるので、試験もそこへ寄せる。

自動で確かめるもの。

- **中身の組み立て** — イベントの列を与えて、1 通の中に起きた順で並ぶか。回答だけが飾りの無い地の文になること、推論が全文のまま伸びて終われば縮むこと、ツールが段階を書き換えること、打ち切りを complete と書かないこと、委譲が一段内へ寄って終われば 1 行になること、絵文字が混ざらないこと、回答の後ろに何も付かないこと。
- **分割** — 上限を超えたときに、コードブロックが (引用の中のものも) 閉じたまま分かれること。
- **停止** — そのチャンネルで走っているものに届き、走っていなければ何もしないこと。
- **消えたものの片付け** — 並びから消えたメッセージが実際に消されること。消せなかった場合でも、後続の投稿が続くこと。
- **本文の分割** — 2000 文字を超えたときの切れ目。コードブロックの内側で切られないこと。
- **入力の整形** — メンションの表記が取り除かれ、発言者が前置されること。
- **送信の間引き** — 間隔内に複数のイベントが来ても 1 回にまとまること、内容が変わらなければ送らないこと、429 を受けたら間隔が伸び、回復すれば戻ること。時刻と送信先を差し替えて確かめる。
- **チャンネルからの引き当て** — 同じチャンネルからは同じ会話が返り、二重に作られないこと。

手で確かめるもの。実際の Discord とモデルが要る。

- メンションで反応し、メンションが無ければ反応しないこと。
- 生成中に「入力中」が出て、終わると消えること。承認待ちの間は出ないこと。
- 推論が伸びていき、終わると「推論: n 秒」へ縮み、伸びていた分が消えること。
- ツール実行と委譲が起きた順に並び、書式で見分けられること。
- 委譲の中で経過が動き、終わると 1 行へ単純化されること。
- 長い回答が分割されること。
- **コマンドの見分け**を、大文字小文字・後ろに引数がある場合・先頭以外の `/` について検証する。
- **コマンドがエージェントへ流れないこと**、逆に `/` で始まらない呼びかけが流れることを検証する。ここが逆になると、止めたいという依頼が生成の順番待ちに並ぶ。
- **`/clear`** が履歴だけを消し、会話とチャンネルの結び付きを残すことを検証する。生成中に断ることも。
- 生成中に `/stop` を打つと、そこで止まること。
- 承認ボタンを本人が押せて、他の人が押せないこと。期限切れで拒否になること。
- 設定でトークンを入れ替えて、再起動せずに繋ぎ直ること。
- 2 つのチャンネルから同時に呼んで、互いを待たずに走ること。

## リスクと未決事項

- **トークンが設定ファイルに平文で載る。** 既存の検索 API 鍵と同じ扱いだが、Discord のトークンはボットの完全な権限そのものなので、漏れたときの範囲が広い。設定ファイルの権限より強い保護は今回入れない。
- **ボットが届く範囲の全員が Ivis を使える。** メンションできる人は誰でも依頼でき、ツールも動く。承認ボタンだけは呼びかけた本人に限るが、その本人が誰であるかの制限はない。範囲を絞るのは招待の管理でやることになる。#694381 で「到達できる範囲は利用者が絞る」と決めた線をそのまま延ばしている。
- **編集の間隔は実測が要る。** 1.5 秒は当たりを付けた値で、実際に 429 が出る頻度を見て決め直す。バックオフを入れておくので、外していても壊れはしない。
- **待ち行列を作るかは使ってから決める。** いまは走っている間の依頼を断る。断られたことは分かるので、実際に困るかどうかを見てから考える。
- **切断中の取りこぼし。** 再接続時にどこまで再送されるかはライブラリと Gateway の挙動次第で、確実ではない。
- **巻き戻しても Discord のメッセージは消えない。** Web で戻した後にチャンネルを見ると、Ivis 側には無いやり取りが残っている。ワークスペースを戻さないのと同じ割り切りだが、こちらは人の目に触れる。
- **実モデルでの動作は未確認のまま。** 委譲や推論の表示は、実際に走らせないと確かめられない部分が残る。これは Discord 連携に限らず、#528664 と #470913 から続いている。
