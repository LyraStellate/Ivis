## 背景と課題

Ivis はこれから作る新規プロジェクトで、リポジトリはまだ空である。したがって本書は「既存コードのどこを直すか」ではなく、**技術スタックを含む土台の決定そのもの**を対象にする。

解きたい問題は次の点にある。

- ローカル LLM を使う汎用チャット UI は既にいくつもあるが、**エージェント定義とスキルを持ち込んで動かせるもの**は少ない。あっても Python + 重量級フレームワーク構成で、常駐させるには重い。
- 一方、Claude Code 形式のスキル資産(`SKILL.md` を持つディレクトリ群)は既に手元に蓄積されており、これをローカルモデルから使う手段がない。スキルは単なるプロンプト断片ではなく、説明文で選択され、必要になってはじめて本文が読み込まれ、同梱スクリプトを実行できる、という仕組みごと移植する価値がある。
- エージェントを複数持ち、親から子へ仕事を投げられること(委譲)は、後から足すと会話履歴の構造とツール実行ループの両方を作り直すことになる。v1 の骨格に入れておく必要がある。

## ゴール / 非ゴール

### ゴール

- Ollama に接続し、ブラウザ上で普通に会話できる。ストリーミング表示、会話の中断、再読み込み後の履歴復元ができる。
- 画面はチャット本体と左パネル(セッション一覧、エージェント選択、設定)で構成する。
- エージェントを JSON ファイルで複数定義でき、セッションごとに選べる。エージェントは他のエージェントへ仕事を委譲できる。
- Claude 形式の md スキルをそのまま読み込める。説明文による選択、本文の遅延読み込み、同梱スクリプトの実行まで動く。
- 単一バイナリで配布でき、起動が速く、待機中の常駐メモリが小さい。

### 非ゴール

以下は「できないから外す」のではなく、**v1 では意図的にやらない**と決めたものである。

- **Ollama 以外のプロバイダ対応。** 内部にプロバイダ抽象は設けるが、実装は Ollama のみ。抽象を用意する目的は将来のためではなく、テストでモックを差し込めるようにするため。
- **任意のシェル実行ツール。** v1 ではファイル操作とスキル同梱スクリプトの実行までに限る。汎用シェルを持たせると、承認フローとサンドボックスの設計が v1 に必要になり、土台作りが終わらなくなる。土台が済んだ後に[ツール拡張 #470913](2026-09-04-agent-tools-%23470913.md)で解禁した。
- **認証・マルチユーザー。** 単一利用者を前提にする。待ち受けアドレスは設定できるようにするが、誰が繋いできたかを問わない。したがってループバック以外へ束ねる場合は、到達できる範囲そのものを利用者が絞る前提になる (VPN の内側など)。[Discord 連携 #617204](2026-09-04-discord-bridge-%23617204.md) で入口が増えても、この前提は変わらない。ボットへメンションできる相手は誰でも依頼でき、絞るのは招待の管理でやることになる。
- **ネイティブアプリ化、モバイル対応。**
- **RAG、ベクトル検索、ファイル添付、画像入力。**
- **MCP サーバー連携。** ツール抽象はこれを後から足せる形にしておくが、v1 では実装しない。
- **スキル/エージェントの配布エコシステム。** ローカルのディレクトリを読むだけ。

## 設計案

### 採用案

**Go で書いた単一バイナリが、HTTP サーバーとエージェント実行エンジンを兼ねる。** フロントエンドは静的アセットとしてビルドし、バイナリに埋め込む(`go:embed`)。利用者はバイナリを起動してブラウザで localhost を開く。

この形を採る理由は「軽量」の中身を次の 3 つに分解したうえで、いずれも満たすからである。

1. **配布が軽い** — ランタイム同梱もインストーラーも不要で、ファイル 1 つを置けば動く。cgo を使わない構成にしてクロスコンパイルを保つ。
2. **実行が軽い** — 待機中はほぼ HTTP サーバーだけが動いている状態になる。推論の重さは Ollama 側にあり、Ivis 自身が重くなる理由がない。
3. **依存が軽い** — HTTP サーバー、SSE、JSON、並行処理が標準ライブラリで完結し、外部依存はデータベースドライバ程度に抑えられる。

永続化は SQLite を用いる。cgo を必要としない純 Go 実装のドライバを使い、単一バイナリという前提を崩さない。

フロントエンドは Svelte + Vite でビルドする。コンパイル結果にフレームワークのランタイムがほとんど残らず、埋め込むアセットが小さくなるため。

トークンのストリーミングはサーバー送信イベント(SSE)で行う。通信が一方向で足り、WebSocket と違って再接続とプロキシ通過が素直に済むため。

### 検討した代替案

- **Tauri によるデスクトップアプリ。** 配布物としてはこちらのほうがアプリらしく、常駐メモリも小さい。却下したのは、Rust ツールチェーンを前提にすると開発環境が重くなること、そして **サーバー機を SSH 越しに使う経路が塞がる**ことによる。Ollama を別マシンで動かす構成は十分あり得るのに、GUI だけがローカルに固定されるのは噛み合わない。
- **TypeScript(Node/Bun)での実装。** AI 周辺のライブラリが最も揃っており、フロントと言語を統一できる。却下理由は待機時の常駐メモリと、ランタイム同梱によって配布物が膨らむこと。単一実行ファイル化の手段はあるが、軽量性を最優先する本件では Go のほうが素直に目的に届く。
- **CLI/TUI を先に作り、GUI を後から載せる。** 最も軽く、最短で動く。却下したのは、要件にあるチャット画面と左パネルが v1 に載らず、「基本的な汎用 AI チャットツールを作る」という目的そのものが達成できないため。
- **既存のローカル LLM チャット UI をフォークして拡張する。** 初期コストは最小になる。却下したのは、そうしたツールが既に独自のエージェント概念とプラグイン機構を持っており、本書が定義するエージェント JSON と Claude 互換スキルを載せるには、既存の抽象と衝突させながら改造することになるため。土台から作るほうが結果的に速く、後の変更も自由が利く。
- **永続化を SQLite ではなく JSON ファイル群にする。** 依存が減り、履歴を手で読める利点がある。却下したのは、セッション一覧の表示や検索のたびに全ファイルを走査することになり、履歴が増えるほど左パネルの表示が重くなるため。なお **エージェント定義とスキルはファイルのままにする**(後述)ので、「手で編集できる」という利点は必要な場所では失われない。

## 詳細設計

### データモデル

情報を **ファイルが正であるもの** と **データベースが正であるもの** に分ける。この区別が本設計の中心にある。

**ファイルが正:エージェント定義・スキル・設定**

利用者が手で編集し、git で管理し、他人と共有する対象である。これらをデータベースに取り込むと、編集のたびに UI を経由させるか同期処理を書く必要が生じ、どちらも利用者の自由を削る。したがって起動時と明示的な再読込時にファイルから読み、Ivis 側は書き戻さない。

例外は初回起動時の雛形出力に限る。設定ファイルもエージェント定義も 1 つも無い状態では
何も起動できず、利用者は空の画面から書式を推測することになる。既にファイルがある場合は
一切触らない。

- **エージェント定義**(JSON、1 エージェント 1 ファイル)が持つ情報は、識別子、表示名、使用するモデル、指示文(システムプロンプト)、許可するツール、利用可能とするスキルの範囲、委譲先として呼べる子エージェント、生成パラメータ。識別子はファイル名から導出し、一覧内で一意であることを起動時に検証する。
- **スキル**は Claude Code の形式に合わせる。ディレクトリの中に `SKILL.md` があり、その冒頭の frontmatter が `name` と `description` を持ち、同じディレクトリに参照ファイルや実行スクリプトを同梱できる。この形式は**外部と既に合意済みの契約**であり、Ivis が独自形式を定義してよい箇所ではない。
- **設定**は単一ファイルとし、Ollama の接続先、既定エージェント、エージェントとスキルの探索パス、待ち受けポートを持つ。

探索パスは複数指定でき、Claude の既存スキル置き場をそのまま指定できることを要件とする。同名スキルが複数のパスに存在する場合は先に指定されたパスを優先し、衝突した事実をログと設定画面に出す。黙って一方を捨てると、利用者は編集したはずのスキルが反映されない理由に辿り着けない。

**データベースが正:セッションと会話履歴**

- **セッション**は 1 つのエージェントに結び付き、表示用のタイトルと更新時刻を持つ。エージェント定義が後から編集・削除されても、セッションは識別子を保持したまま残る(削除済みエージェントのセッションは開けるが続行はできない、と UI で示す)。
- **メッセージ**は役割、本文、生成に用いたモデル、時刻を持つ。加えて、ツール呼び出しとその結果、および**どの委譲実行に属するか**を表現できる必要がある。子エージェントの実行過程は親の会話に平坦に混ぜず、親メッセージにぶら下がる形で保持する。UI で折りたたんで見せるためであり、混ぜてしまうと後から構造を復元できない。

満たすべき制約は次の通り。

- 生成中にプロセスが落ちても、それまでに確定した内容が失われない。ストリーミング中の部分出力は一定間隔で書き込む。
- 履歴の書き込み失敗は握り潰さず、UI にエラーとして出す。会話が保存されていないのに保存されたように見える状態を作らない。
- セッションの削除はそのセッションのメッセージのみを消し、エージェント定義とスキルには一切影響しない。

### インターフェース

**フロントエンドから見た HTTP API** で提供する操作は次の通り。

- セッションの一覧・作成・改名・削除、および 1 セッションの履歴取得。
- メッセージ送信。応答は SSE のストリームで返し、トークン片、ツール呼び出しの開始と結果、委譲の開始と終了、承認要求、完了、エラーをイベントとして流す。
- 生成の中断。
- エージェント一覧とスキル一覧の取得、および両者の再読込。
- 設定の取得と更新。
- ツール実行に対する承認応答。

失敗は利用者が次に何をすべきか分かる粒度で区別する。少なくとも「Ollama に接続できない」「指定モデルが Ollama 側に存在しない」「エージェント定義の読み込みに失敗した(どのファイルか)」「スキルの読み込みに失敗した(どのスキルか)」は別物として扱う。これらをまとめて「エラーが発生しました」にすると、利用者は Ollama を起動し忘れているのか設定を間違えたのか判断できない。

**内部の抽象**は次の 4 つに絞る。

- **プロバイダ** — 会話履歴とツール定義を受け取り、トークン列とツール呼び出しをストリームで返す。v1 の実装は Ollama のみ。
- **ツール** — 名前、入力の形、説明、実行手続き。ファイル操作、スキル読み込み、委譲がこれにあたる。
- **スキルレジストリ** — 探索パスからスキルを読み、一覧(名前と説明)と本文の取得を提供する。
- **エージェントランナー** — 上記を束ね、1 ターンの実行ループを回す。

承認は SSE 上の「承認待ち」イベントと専用エンドポイントの応答で往復させる。応答があるまで実行ループは待ち、待機中も中断できる。

### 処理フロー

**通常のターン**は次の順で進む。セッションからエージェントを解決し、システムプロンプトを組み立てる。組み立てに含めるのは、エージェントの指示文、利用可能なツールの定義、そして**利用可能なスキルの名前と説明の一覧**である。スキル本文はここに含めない。含めればスキルが増えるほど毎ターンの入力が膨らみ、ローカルモデルの限られた文脈長をすぐ食い潰す。モデルが必要と判断したときにスキル読み込みツールを呼び、そこではじめて本文を会話に入れる。

以降はツール呼び出しがなくなるまでのループになる。モデルの出力をストリームで流しながら、ツール呼び出しが現れたら承認を挟んで実行し、結果を会話に戻して継続する。ツール呼び出しが現れなくなった時点でターンを終え、履歴を確定させる。同一ターン内の反復には上限を設け、上限に達したら打ち切って利用者に理由を示す。ローカルモデルは同じツールを呼び続けるループに入ることがあり、これがないと止まらなくなる。

**委譲**は 1 つのツールとして表現する。親が子エージェントの識別子と依頼内容を渡すと、子は自分自身の指示文とスキル集合を持つ独立した文脈で同じ実行ループを回し、**最終的な成果だけ**が親に戻る。子の途中経過は親の文脈を圧迫しないよう戻さない(履歴には保存し、UI では追える)。委譲の深さと同時実行数には上限を設ける。呼べる子は親のエージェント定義に列挙されたものに限り、循環を実行時に検出して打ち切る。

**異常時の扱い**は次の通り。Ollama への接続が途中で切れた場合、それまでの部分出力を保存したうえでエラーとして示し、続きを再試行できる状態にする。ツールの実行が失敗した場合はエラー内容をモデルに返して継続させる。失敗もモデルにとっては情報であり、こちらで打ち切るより自己修正の機会を与えるほうがよい。承認が拒否された場合も同様に、拒否された事実をモデルに返す。

**実行の安全性**について。ファイル操作ツールとスキル同梱スクリプトは、いずれもセッションに紐づく作業ディレクトリの外へ出られないようにする。判定はシンボリックリンクを解決したうえでの実際のパスに対して行う。文字列としてのパスで判定すると、リンクを経由した境界外アクセスを見逃す。

### 認識しておくべき前提

ここまでの設計は、**モデルがツール呼び出しを扱えること**に依存している。Ollama で動くモデルにはツール呼び出しに対応しないものがあり、その場合はスキル読み込みも委譲も機能しない。v1 では、対応していないモデルを選んだときにその旨を明示する方針を採る(後述の未決事項も参照)。

## テスト方針

- **エージェントランナー**をプロバイダのモックに対して検証する。ツール呼び出しループが正しく終わること、反復上限で打ち切られること、委譲が子の成果だけを親に返すこと、深さ上限と循環検出が効くこと。ここが壊れると全体が壊れるので最も厚くする。
- **スキルローダー**は、実在する Claude スキルのディレクトリを fixture として読み込ませる。frontmatter が欠けている、`SKILL.md` がない、名前が衝突している、といった壊れた入力で落ちずに警告できることまで含める。
- **パス境界の判定**は独立して重点的に検証する。相対パスでの上位参照、シンボリックリンク経由、絶対パス指定を含める。
- **履歴の永続化**は、生成の途中で中断された場合に部分出力が残ることを確認する。
- **手動確認**が必要な範囲として、実際の Ollama に小さいモデルを載せた状態での通しの動作、ストリーミング表示の追従、生成中断、ブラウザ再読み込み後の履歴復元、Ollama を停止した状態でのエラー表示を挙げる。

## リスクと未決事項

- **ローカルモデルのツール呼び出し精度。** これが低いと、スキル読み込みも委譲も呼ばれないか誤って呼ばれる。ツール非対応モデル向けにテキストベースの代替プロトコルを用意するかどうかは未決とし、実際のモデルで試してから決める。先に作ると、必要なかった場合に捨てる量が大きい。
- **Claude スキルの互換範囲。** 既存スキルの一部は Claude Code 固有のツールや環境を前提にしており、読み込めても意図通りには動かない。どこまでを互換とみなし、動かないものをどう利用者に示すかは、実際のスキルを読み込ませながら決める。
- **承認の粒度。** 毎回確認するか、セッション内で記憶するか、自動許可の一覧を設けるか。毎回確認は安全だが実用性を損なうため、実際に使いながら決める。
- **純 Go の SQLite ドライバの性能。** 想定する履歴規模では問題ないと見込んでいるが未検証。左パネルの一覧表示が遅くなるようなら、一覧に必要な情報だけを別に持つ形に変える。
- **ポート衝突と多重起動。** 既定ポートが埋まっていた場合の挙動、および同じ設定で 2 つ起動されたときにデータベースをどう扱うかを決めていない。
- **フロントエンドのビルドを配布物に含める運用。** 埋め込み方式を採る以上、ビルド手順が 2 段になる。開発時に毎回フロントをビルドせずに済む導線を用意しないと、日々の開発が煩わしくなる。
